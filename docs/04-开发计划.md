## 零、这份文档怎么用

> **给所有 AI 终端的说明**：本文件是项目的**唯一进度真相来源**。
> 每次开始工作前，先读本文件确认当前阶段；完成一个任务后，**立即更新对应任务的状态标记**。

### 状态标记约定

| 标记 | 含义 |
|------|------|
| `[ ]` | 未开始 |
| `[~]` | 进行中 |
| `[x]` | 已完成 |
| `[!]` | 阻塞（必须写明阻塞原因） |

### 交接规则（**关键**）

1. 完成一个任务后：
   - 勾选对应任务项
   - 在「附录 A · 开发日志」追加一条记录（日期 / 做了什么 / 文件 / 遗留问题）
2. ⛔️ **同步文档是"完成"的一部分，不是可选项** —— 每次改动（**改产品口径 / 改代码 / 改数值**）都必须
   在同一次改动里把这些**登记类文档**同步掉，否则它们会立刻变成误导源：
   | 动了什么 | 必须同步哪里 |
   |---------|------------|
   | 修了 [09 待决问题总表](./09-待决问题总表.md) 里的条目 | **把条目从"未决"移入 §四 已收敛**（不是只改内容） |
   | 任何影响获取成本的数值（冷却 / 上限 / 等级曲线 / 互动经验） | **重跑 `tools/acquisition_sim.py`** 并同步 [08](./08-获取路径与周期测算.md)（**ADR-024 强制**） |
   | 新增/删除领域字段 | [03 §3~4 表结构](./03-数据库设计.md) + [03 §5 迁移](./03-数据库设计.md) + `PetMapper` + 往返测试（**"派生但必须持久化"**） |
   | 新增 `ItemEffect` / 道具 | [11 §五 消耗表](./11-经济系统设计.md) |
   | 测试增删 | [05 概览](./05-AI开发交接指南.md) · [06 §六](./06-物种与稀有度设计.md) 的计数（**只认 `core/build/test-results/`**） |
   | 改了物种/稀有度/形态 | [06](./06-物种与稀有度设计.md) · [07](./07-五虫体系设计.md) |
   | 引入新的"待决" | **登记进 [09](./09-待决问题总表.md)**，不要只在对话里说 |
3. 开始新阶段前：确认**前置依赖**已全部完成
4. 遇到阻塞：标记 `[!]` 并在日志中写明原因，**不要跳过继续做后面的**

| 变更 | 说明 | 关联 |

### 新阶段总览

```
Phase 0  工程骨架            ── ✅ 已完成
   ↓
Phase 1  核心养成闭环         ── 盲盒→孵化→破壳→互动（帧动画占位）
   ↓
Phase 2  数据与成长           ── Room 扩展、等级经验、道具背包
   ↓
Phase 3  Rive 渲染 + 桌宠     ── 立体宠物 + 单只悬浮窗跑通
   ↓
Phase 4  桌面多宠场景         ── 3 只同屏、位置引擎、主宠切换  ⭐ 新增
   ↓
Phase 5  桌面生活与事件反应   ── 生活行为、事件总线、多宠反应  ⭐ 新增
   ↓
Phase 6  家庭、配对生育与融合  ── 血缘称谓、配对（真人/NPC）、遗传、融合  ⭐ 重定义
   ↓
Phase 7  后端与社交           ── 账号、同步、族谱、排行榜、串门
   ↓
Phase 8  隐居与长线打磨       ── 后山小屋、召回、传承彩蛋
   ↓
Phase 9  上线准备             ── 性能、合规、商店上架
   ↓
Phase 10（可选）家族公会      ── 原 v1.0 的家族系统，视数据决定
```

> ⭐ **关键排序原则**：**单机可玩 → 桌面体验 → 家庭关系 → 联网社交**。
> 桌面家庭情景是本产品的灵魂，必须在联网前就做扎实。

> ⚠️ **副宠不是"删除"** —— 按 [10 §4.2](./10-融合机制设计.md) 它**「入后山」**：退出桌面与配对、不可取回，但**保留在族谱与图鉴记录里**。所以它对应的实现是 `stage = RETIRED`（与隐居共用终点），**不是 `DELETE`**。这点直接决定 `FusionRepository` 写的是 `UPDATE` 而非 `DELETE`。

**融合的四条硬约束**（算法已守住，UI 与用例**不得绕过**）：
1. **跨物种不可融合** —— 只允许**同物种**，跨物种由 `SPECIES_MISMATCH` 拒绝；
2. **灵兽两侧都禁** —— 灵兽既不能当目标也不能当材料；
3. **神话是融合上限** —— 神话目标直接拒绝，**而不是静默浪费材料**；
4. **永不产出灵兽** —— 灵兽**只能遗传**（ADR-017），融合再多也只到神话。

**Phase 6 验收标准**

## 三、给 AI 终端的接手指引

### 开始工作前必读

1. `05-AI开发交接指南.md` — 开发规范与边界
2. 本文件 — 确认当前阶段
3. `00-产品需求文档PRD.md` — 确认产品语义（**v2.0 已大改，务必读最新版**）
4. 对应的设计文档 — 明确要做什么

### 接手一个新任务的流程

```
1. 在本文件找到状态为 [ ] 且依赖已满足的任务
2. 把状态改为 [~]
3. 阅读该任务对应的设计文档章节
4. 按架构约定实现（遵守 01-技术架构设计.md 第十节代码规范）
5. 写单元测试（UseCase 层强制）
6. 运行 ./gradlew assembleDebug 与 test 确认通过
7. 跑一次合规自检脚本（若有权限相关改动）
8. 把状态改为 [x]
9. 在附录 A 追加开发日志
```

### 禁止事项

- ❌ 跳过依赖直接做后面的阶段
- ❌ 修改已有领域模型的语义（如需修改，先更新文档）
- ❌ 在 UI 层写业务逻辑
- ❌ **在 UI 层或渲染层自算血缘关系**（必须用 `KinshipResolver`）
- ❌ 引入无障碍服务 / 读取第三方 App 的能力
- ❌ **读取其他应用的图标、包名、文本**
- ❌ 使用 `fallbackToDestructiveMigration` 作为长期方案
- ❌ 提交 `keystore` / 密钥 / 签名文件
- ❌ 未经文档同步就改变架构分层
- ❌ **重新引入"结婚"机制**（v2.0 已明确取消，见 PRD §11.1）
- ❌ **在 `SpeciesFamily` 枚举里添加历史别名常量**（如 `BIRD` / `MAMMAL`）。枚举常量是**独立条目**不是别名，会污染 `entries`，导致任何"遍历所有类群"的 UI 出现幽灵项。兼容一律走 `SpeciesFamily.fromName()` 字符串映射
- ❌ **让「灵兽」或「异兽」进入任何抽取池**。灵兽只能由 `BreedingRules.offspringRarity`（含灵血觉醒）产生，异兽物种只能由 `offspringSpecies` 产生；所有抽取路径必须使用 `Rarity.drawableEntries()` 与 `PetSpecies.drawableEntries()`，任何"保底/指定稀有度"能力都必须经 `Rarity.maxDrawable` 钳制
- ❌ **破坏跨虫/同虫上漂系数的单调序**（`1.0 < 1.35 < 1.8 < 2.0`），否则跨虫社交激励反转
- ❌ **在客户端生成生育结果**（必须服务端下发，见 ADR-015）
- ❌ **为蠃虫补拟人化/萌化的替代神兽**（如"螺贝之灵"）。应保持"依据典籍不设"的立场，而非"不敢做找替身"（见 ADR-020）
- ❌ **在属性/战力/升级公式中引入 `SpeciesFamily`**。`PetAttributes.ofLevel` 只接受 `Rarity` + 物种级 `tendency`，五虫不参与数值（见 ADR-021）

| **ADR-025** ⭐ | **桌宠窗口采用「1 个全屏渲染窗 + 每宠一个触摸窗」**（修订 ADR-014） | ADR-014 只推演了渲染性能（1 窗口 + N 节点），**未覆盖触摸穿透**；而 Android 的触摸是窗口级的，全屏窗"可点"与"不挡桌面"不可兼得。真机实测（Xiaomi Mi 9 Pro 5G / Android 11）确认分层可行。**不用"每宠一个渲染窗"的决定性理由：独立窗口物理上无法绘制跨宠物动画**，而「一家三口」（互相蹭头、粒子从 A 飘到 B、一起睡）正是核心卖点 | 2026-10-16 |

> **ADR-025 附**：实测证据与 3 个踩坑（**位置必须钳制**、**拖动要用累计位移 + touch slop**、
> **必须用 `rawX/rawY` 而非 `x/y`**）见 [99 §六](./99-桌宠技术验证操作单.md)；
> 实现约束见 [02 §3.5](./02-宠物渲染方案.md)。
> ⚠️ 剩余风险：**仅小米 ROM 通过**（华为/OPPO/vivo 空白），且**3 只宠物同屏未实测**。

| **ADR-026** ⭐ | **神兽形态拆两层，完整形态层由「灵兽 × 同虫」独占**（解决 S12） | 改造前"稀有度 ≥ 传说即自动获得"有两个后果：① **神兽沦为抽卡的免费赠品**（无门槛、无动作、无获得感）；② **同虫配对没有任何存在理由**（加成 ×1.00 严格劣于跨虫 ×1.35，同虫出异兽又只有 1%）。拆开后 `跨虫→异兽` / `同虫→神兽形态` 各有专属领地，且**不需要给同虫加任何数值**（守住 ADR-021）。⚠️ **已知代价**：灵兽会分两种长相（跨虫灵兽没有完整形态层）—— 同虫因此慢约 8%（65 天 vs 60 天），但同虫同时享有 100% 成功率与"只需另一只同虫宠"的可得性优势 | 2026-10-16 |

> **ADR-026 附 · 形态是"个体属性"，必须落库**：
> 判定需要"诞生时的配对类型"这个信息，而宠物自身推不出来
> （`parentIdA/B` 只指向父母，无法反推当时是同虫还是跨虫）。
> 因此新增 `pet.deity_form` 列 + `MIGRATION_2_3` + `PetMapper` 双向映射 + 往返测试。
> **这是 `exotic_blood` 事故之后第一次同类改动，这次一次补齐，没有重犯。**
>
> 📌 **两层通道不能混**：`hasDeityFeatures` ← 稀有度 ≥ 传说（抽卡回报，纯推导）；
> `hasDeity` ← `Pet.hasFullDeityForm`（出生结算，持久化）。跨虫灵兽是
> `features=true / hasDeity=false` 的**合法组合**，美术别当异常。
