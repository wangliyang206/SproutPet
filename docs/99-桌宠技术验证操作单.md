## 〇、这次到底在验证什么

产品最大的卖点是「宠物跑到桌面上，能坐在其他 App 的图标上」。
它依赖一个前提：**全屏透明悬浮窗能显示，同时不影响用户点桌面上的其他东西。**

问题在于 Android 的窗口触摸是**窗口级**的，没有"部分区域可穿透"的 API：

| 窗口设置 | 结果 |
|---------|------|
| 加 `FLAG_NOT_TOUCHABLE` | 整个窗口都不收触摸 → 事件全穿透 → **宠物点不动** |
| 不加 | 整个窗口都收触摸 → 事件被吃掉 → **桌面点不动** |

所以必须用「渲染窗口 / 触摸窗口」分离来绕（ADR-014 只推演了渲染性能，**没覆盖触摸穿透**）。

**这次验证要回答的就是：桌宠能不能"可交互"且"不挡桌面"。如果答案是不能，产品定位要重新考虑。**

## 一、你只需要做三步

### 第 1 步 · 装包

```bash
cd E:\git\SproutPet
./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

（也可以把 `app-debug.apk` 直接拷到手机里点安装）

> ⚠️ debug 包的包名带 `.debug` 后缀（`com.sproutpet.pet.debug`），与正式包可共存。

### 第 2 步 · 开权限

打开 App → 右上角「**桌宠验证**」→ 点「**去开启悬浮窗权限**」→ 在系统设置里打开。

> 不同品牌叫法不同：悬浮窗 / 显示在其他应用上层 / 在其他应用上层显示。

也可以命令行直接进面板：

```bash
adb shell am start -n com.sproutpet.pet.debug/com.sproutpet.pet.debug.DesktopPetProbeActivity
```

### 第 3 步 · 跑四个模式，然后分享日志

**每个模式的动作完全一样**，重复四次：

| 顺序 | 动作 |
|------|------|
| 1 | 点「**启动 ①**」（点完会自动退回桌面） |
| 2 | 屏幕上出现一个绿色圆点（写着「宠」） |
| 3 | **拖它一下** → 看跟不跟手 → 点按钮记录：`拖动：跟手` 或 `拖动：不动` |
| 4 | **点它以外的地方**（比如桌面上的时钟图标）→ 看图标有没有被点开 → 点按钮记录：`空白：能点桌面` 或 `空白：点不到` |
| 5 | 从**通知栏**点回验证面板 |
| 6 | 换下一个模式，重复 |

四个模式（①②③④）都跑完 → 点最下方「**分享日志（发给我）**」→ 发到微信 / 邮件 / 任意地方即可。

> 💡 「人工观察」那几个按钮**点错了没关系**，再点另一个就是。它们只是往日志里写一行结论。
> 有些结果代码测不到（比如"桌面图标有没有被点开"——那个事件根本不经过我们的进程），所以才需要你看一眼后点一下按钮。

## 二、每个模式应该看到什么

| 模式 | 配置 | 拖动宠物 | 点空白处 |
|------|------|---------|---------|
| ① 全屏渲染 · 全穿透 | 全屏窗 + `NOT_TOUCHABLE` | ❌ **拖不动**（预期如此） | ✅ 能点到桌面 |
| ② 全屏可点 · 挡桌面 | 全屏窗不加 flag | ✅ 跟手 | ❌ **点不到**（故意做的反例） |
| ③ 全屏渲染 + 触摸小窗 | 全屏穿透窗只画 + 宠物大小小窗只收触摸 | ✅ 跟手 | ✅ 能点到桌面 ← **⭐ 最关键** |
| ④ 独立小窗 | 每宠物一个自渲染小窗 | ✅ 跟手 | ✅ 能点到桌面 |

**判定要点**：

- 模式 ① 如果**能拖动宠物**，说明 `FLAG_NOT_TOUCHABLE` 没生效 → 穿透方案有变数
- 模式 ① 如果**出现黑框/灰底**，说明窗口透明有问题，先排查这个再看别的
- 模式 ③④ 如果**点空白处点不到桌面**，说明「渲染 / 触摸分离」在当期 ROM 上不成立 → **产品定位需要重新设计**
- 模式 ② 的"点不到"是**故意**的，用来证明"全屏可点"的代价有多大
- 顺带留意：把宠物拖到**屏幕边缘**是否被裁剪、位置是否正确

## 三、必测机型

国产 ROM 对悬浮窗都有各自的魔改，**至少覆盖三类**：

| 品牌 | 系统 | 备注 |
|------|------|------|
| 小米 / 红米 | MIUI / 澎湃 OS | 悬浮窗策略最严，优先测 |
| 华为 / 荣耀 | EMUI / HarmonyOS / MagicOS | 需单独确认是否有额外白名单 |
| OPPO / vivo | ColorOS / OriginOS | 后台与悬浮窗限制各不相同 |
| 原生 / AOSP（Pixel 等） | — | 作为**基准对照**，AOSP 跑通不代表国产机器能跑通 |

### 顺手记录（可选）

| 观察项 | 说明 |
|-------|------|
| 通知栏是否常驻 | 前台服务通知能否正常显示 |
| 息屏再亮屏后宠物是否还在 | 窗口是否被系统回收 |
| 切换 App 后宠物是否还在 | 是否被其他全屏应用顶掉 |
| 长时间挂着是否被系统杀掉 | 保活能力 |
| 宠物在状态栏区域能否显示 | `FLAG_LAYOUT_NO_LIMITS` 效果 |
| 是否有耗电/发热异常 | 悬浮窗空转的影响 |

## 五、附录 A：日志怎么读（分析者用）

| 日志标签 | 含义 |
|---------|------|
| `[WINDOW] OK/FAIL` | 窗口创建成功/失败、类型与 flags、尺寸。FAIL 说明该 ROM 拒绝此类窗口 |
| `[TOUCH]` | 触摸事件到达我们的窗口（**没出现 = 事件没到我们这**） |
| `[TEST]` | 该模式的操作提示 |
| `[SVC]` | 服务状态、宠物初始位置 |
| `[OBSERVE]` | 测试者点击的**人工结论** |
| `[ERROR]` | 添加/移动窗口失败（记录异常类型与消息） |

**判断口诀**：

- **没看到 `DOWN` 日志，但桌面有反应** → 事件完全穿透，我们收不到 ✓（模式①的目标）
- **看到 `DOWN` 日志，桌面无反应** → 事件被我们吃掉（模式②③④的宠物区域）
- **点空白看到 `DOWN 落在空白`，且桌面无反应** → 全屏窗口挡住了桌面 ✗（模式②的代价）

另外关注：事件坐标是否与未捕获的触摸一致（判断有没有坐标偏移）、`CANCEL` 是否频繁（判断 ROM 是否额外干预）。

## 六、结论记录（2026-10-16 实测）

### 设备信息

| 项 | 值 |
|----|----|
| 机型 | Xiaomi Mi 9 Pro 5G |
| 系统 | **MIUI / Android 11（SDK 30）** |
| 测试日期 | 2026-10-16 10:43 ~ 10:45 |
| 覆盖度 | ⚠️ **仅 1 台 / 4 类 ROM**（操作单要求小米/华为/OPPO+vivo/原生） |

### 四模式结果

| 模式 | 是否实测 | 窗口挂载 | 拖动 | 空白穿透 | 备注 |
|------|---------|---------|------|---------|------|
| ① 全屏渲染 · 全穿透 | ❌ 本轮未跑 | — | ❌ 结构上必然拖不动 | ✅ 必然穿透 | `FLAG_NOT_TOUCHABLE` 写死在代码里，宠物永远收不到触摸 |
| ② 全屏可点 · 挡桌面 | ❌ 本轮未跑 | — | ✅ 必然跟手 | ❌ 必然挡桌面 | 全屏窗口吃掉所有事件，是**故意做的反例** |
| ③ 全屏渲染 + 触摸小窗 | ✅ **跑了 2 轮** | ✅ 无 FAIL | ✅ 跟手（14 次） | ✅ 口述通过 | ⭐ **采用** |
| ④ 独立小窗（自渲染） | ✅ 跑了 1 轮 | ✅ 无 FAIL | ✅ 跟手（6 次） | ✅ 口述通过 | 可行，但**放弃**（理由见下） |

> ① ② 的"弊端"是**代码结构决定的**，不是 ROM 差异导致的运气问题，所以不测也能定论。

### 日志给出的硬证据

**窗口层（③，第 1 轮）**

```
[WINDOW] OK 全屏窗口(穿透) flags=0x1000218 size=-1x-1
[WINDOW] OK 触摸小窗(透明) flags=0x1000208 size=302x302
```

把 flags 拆开看，两点都正确：

| 窗口 | flags | 含义 |
|------|-------|------|
| 全屏渲染层 | `0x218` | `FLAG_LAYOUT_NO_LIMITS` + **`FLAG_NOT_TOUCHABLE`** + `FLAG_NOT_FOCUSABLE` |
| 宠物触摸层 | `0x208` | `FLAG_LAYOUT_NO_LIMITS` + `FLAG_NOT_FOCUSABLE`（可触摸） |

**交互（③ 14 次拖动 + 8 次点击；④ 6 次拖动 + 3 次点击）**

- 全部 `DOWN → 开始拖动 → UP 拖动结束` 成对出现，**零 `[ERROR]`、零 `ACTION_CANCEL`** → 该 ROM 没有额外干预触摸流
- 点击宠物时记录 `UP 点了宠物一下（本次点击未传给桌面）` → 宠物区确实被我们独占

### ⚠️ 日志**没有**证明的那一条（必须说清）

**"点宠物以外的空白，桌面图标能否点开" —— 日志里一条记录都没有。**

原因是结构性的：如果穿透成功，事件**根本不经过我们的进程**，日志里必然是空的。而且本轮**没有点过「人工观察」按钮**（日志里 0 条 `[OBSERVE]`）。

所以这一条目前**只有测试者的口述**，不是日志证据。

> ✅ 但它**在架构上是结构性成立的**，不依赖运气：
> 全屏层带 `FLAG_NOT_TOUCHABLE`（框架级保证不收触摸），触摸层只有 302×302。
> 两者相减 ⇒ 宠物以外的区域**没有任何属于我们的可触摸窗口**。这是推演可证的，实测只是佐证。

### 🐞 顺带发现的 3 个问题

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| 1 | **宠物能被拖出屏幕，没有边界钳制** | ③ 出现 `停在 (-137, 739)` / `(-215, 632)` / `(960, 857)`。屏宽 1080、宠物 302 ⇒ 合法 x 范围应是 `0..778` | 宠物跑出屏幕就**找不回来了**。④ 同样没有钳制，只是这轮手没拖狠 |
| 2 | **慢速拖动会完全失效** | 代码每次 `ACTION_MOVE` 都重置基准点、要求单帧位移 ≥ 6px 才移动（≈ 360px/秒）。慢拖时每帧位移不足 6px 会被**整段丢弃**，宠物纹丝不动，松手还被判定为"点击" | 日志里拖得干脆所以没暴露，但真实用户一定会遇到 |
| 3 | **③ 的日志打印了模式①的文案** | 第 11、96 行：`[TEST] 现在连点【宠物圆】都应该穿透到桌面 —— 这是模式①的关键验证点`。来源是 `attachFullScreenWindow(touchable=false)` 无条件输出 | 读 ③ 的日志时会被误导 |

### ⚠️ 还有一个钳制带来的副作用（要在生产版提前想）

一旦把宠物**钳制在屏幕边缘**，手指还能继续往外滑 → 手指离开 302px 的触摸小窗 → 小窗收到 `ACTION_CANCEL` → **拖动被系统中断**。

两个可选解：

- **A（推荐）**：触摸窗做得比宠物视觉大一圈（如四周各 +24dp），手指滑出屏幕边缘时仍落在窗内
- **B**：接受"拖到边就停"，收到 `CANCEL` 时按当前钳制位置优雅结束

### 最终采用的方案

**☑ ③ 全屏渲染 + 触摸小窗**

**为什么不用 ④**（虽然 ④ 窗口更少）：

1. **④ 每只宠物一个渲染窗 ⇒ 跨宠物动画在物理上不可能。** 而「一家三口」正是核心卖点：两只宠物互相蹭头、心形粒子从 A 飘到 B、一起睡 —— 这些都需要**共享画布**，在 ④ 里会被各自窗口的边界直接裁掉。
2. **ADR-014 的原始意图在 ③ 里成立**：1 个渲染面 + N 个 Rive 节点、统一帧调度、单实例纹理。
3. **④ 想补回跨宠物效果，最后还是得再加一个全屏特效窗** → 变成 ③+④ 混合，比 ③ 更差。
4. ③ 的窗口数是 **1 个渲染窗 + N 个触摸窗**（3 只宠物 = 4 个窗口）。触摸窗是**纯透明、不渲染**的，开销远低于一个渲染窗。

### 未能通过的机型与原因

暂无。⚠️ 但**华为 / 荣耀、OPPO / vivo 尚未测试**，不能宣布"全机型可用"。

### 本轮未覆盖、需要后续补测的项

| 项 | 为什么重要 |
|----|-----------|
| **3 只宠物同屏** | 3 个触摸窗互不干扰、窗口层级、渲染性能，全都没实测。这是**真实产品场景** |
