## 版本变更说明（v1.0 → v2.0）

| 变更项 | v1.0 | v2.0 |
|-------|------|------|
| 服务端定位 | 预留（Phase 6 再说） | **依然是"预留但必须落地"**，且从"排行榜/家族"升级为**配对生育刚需** |
| 桌面渲染 | 单只悬浮窗 | **多只同屏（≤3）** + 事件总线 + 景深分层 |
| 关系模型 | `Marriage` | **`Pairing` + 血缘关系图**（无婚姻） |
| 新增子系统 | — | **桌面事件总线、关系推导引擎、家庭情景导演** |
| 新增模块 | — | `pet/desktop/`（桌面场景编排）、`domain/family/`（血缘与称谓） |
| 生命周期 | 成年/长者 | 增加 **`Retired`（隐居）** 状态与"后山小屋"场景 |
| 声音 | 未定义 | 气泡层（独立悬浮 TextView）+ 可选音效通道 |

### v2.0 → v2.1 增量（代码已落地）

| 变更项 | v2.0 | v2.1 |
|-------|------|------|
| 稀有度 | 5 档 | **6 档**，新增不可抽取的「灵兽」（`Rarity.isDrawable` / `drawableEntries()`） |
| 物种分类 | 4 类群 / 12 种（禽兽羊异） | **五虫体系 6 类群 / 18 种**（`SpeciesFamily` = LUO/LIN/MAO/YU/KUN/UNCATEGORIZED） |
| 遗传算法 | 简单概率 | **加权分布漂移**（`RARITY_DISTRIBUTION` + 基准 `max(父母)` + 类群上漂系数） |
| 关系模型 | `Marriage` | 已全部落地为 `Pairing` / `PairingRules` / `PairingStatus` |

> ⚠️ **架构红线（v2.1 新增）**：`SpeciesFamily` 枚举**只有 6 个值**，历史别名只能存在于 `fromName()` 字符串映射。枚举常量是独立条目而非别名，混入会污染 `entries`。
> ⚠️ **抽取路径必须使用 `Rarity.drawableEntries()`**，不得使用 `Rarity.entries`，否则灵兽会泄漏进抽取池。
>
> ⚠️ **任何"保底 / 指定稀有度"能力，其上限都必须用 `Rarity.maxDrawable` 钳制**（v2.2 新增）。
> 否则一张"灵兽保底券"就能绕开 ADR-017 —— `BlindBoxEngine.draw` 已内置该钳制。

## 一、技术选型总览

| 维度 | 选型 | 版本 | 选择理由 |
|------|------|------|---------|
| 语言 | Kotlin | 1.9.23 | 与现有 TemplateAPP 一致 |
| UI | **XML + ViewBinding** | — | 按需求指定；复杂动画场景比 Compose 更可控 |
| 架构 | **MVVM + Clean 分层** | — | 业务可测试、易并行开发 |
| 异步 | Coroutines + Flow | 1.7.3 | 官方推荐 |
| DI | Hilt | 2.48.1 | 编译期校验 |
| 持久化 | Room + MMKV | 2.5.2 / 1.3.2 | Room 存结构化，MMKV 存轻量配置 |
| 网络 | Retrofit + OkHttp | 2.9.0 / 4.12.0 | 事实标准 |
| 图片 | Glide + Coil | 4.16.0 / 2.5.0 | 静态图 / 动态加载 |
| **宠物渲染** | **Rive** | 9.6.0 | 骨骼形变带来立体感；状态机天然适配互动 |
| 降级渲染 | Lottie | 6.3.0 | 低端机 / 美术未就绪时 |
| **气泡渲染** | 自绘 View / 独立悬浮 TextView | — | 轻量、可控、无额外依赖 |
| 构建 | Gradle + AGP | 8.4 / 8.3.2 | 与 JDK 17 兼容 |
| 最低版本 | minSdk 24 / targetSdk 34 | — | 覆盖 Android 7.0+ |

> ⚠️ **v2.0 新增约束**：多宠同屏要求渲染层支持**多实例复用与统一调度**，不能再每个宠物一个独立 `RiveAnimationView` 各自为政（内存与帧率会失控）。见 §6.6。

## 二、模块划分

```
SproutPet/
├── app/                    # UI 层、导航、桌面场景编排
└── core/                   # 领域模型、数据层、基础设施
```

### 2.1 模块依赖方向

```
        ┌──────────────┐
        │     app      │   ← 可依赖 core（含 Rive 渲染实现）
        └──────┬───────┘
               │ implementation
               ↓
        ┌──────────────┐
        │     core     │   ← 不反向依赖 app
        └──────────────┘
```

**职责切分补充（v2.0）**

| 内容 | 放哪 | 原因 |
|------|------|------|
| 血缘关系推导、称谓计算、基因遗传 | **core/domain** | 纯逻辑，必须可单测 |
| 桌面事件总线（EventBus）定义 | **core/domain/desktop** | 事件语义属于业务 |
| 事件总线实现（Flow 实现） | app | 运行期基础设施 |
| Rive/Lottie 渲染实现 | **app** | 依赖 Android View |
| `PetRenderer` 接口 | **core/domain/pet** | 抽象不被实现污染 |

## 三、分层架构（Clean Architecture 轻量化）

```
┌──────────────────────────────────────────────────────────┐
│  UI 层 (app 模块)                                          │
│  Activity / Fragment / Adapter / ViewBinding / 悬浮窗      │
│  职责：渲染状态、转发用户事件、桌面窗口布局                  │
│  不含：任何业务判断、任何关系计算                            │
└────────────────────┬─────────────────────────────────────┘
                     │ 观察 StateFlow / 调用 ViewModel 方法
┌────────────────────┴─────────────────────────────────────┐
│  ViewModel 层                                             │
│  职责：持有 UiState、编排 UseCase、Resource → UiState      │
│  新增：DesktopViewModel（同屏宠物状态、主宠切换）           │
└────────────────────┬─────────────────────────────────────┘
                     │ 调用
┌────────────────────┴─────────────────────────────────────┐
│  UseCase 层（业务用例）                                    │
│  职责：单一业务动作                                        │
│  新增：PairPetsUseCase / ResolveReactionUseCase /          │
│        SwitchMainPetUseCase / RetirePetUseCase             │
│  特点：纯 Kotlin，无 Android 依赖，100% 可单测              │
└────────────────────┬─────────────────────────────────────┘
                     │ 调用
┌────────────────────┴─────────────────────────────────────┐
│  Repository 层                                            │
│  职责：数据来源编排（本地 Room / 远程 API）                 │
│  返回：Flow<Resource<T>>                                  │
└────────────────────┬─────────────────────────────────────┘
                     │
      ┌──────────────┴──────────────┐
      ↓                             ↓
┌─────────────┐             ┌─────────────┐
│  Room DAO   │             │  Remote API │
└─────────────┘             └─────────────┘
```

### 3.1 各层职责边界（**红线**）

| 层 | 可以做 | **禁止做** |
|----|-------|-----------|
| UI | 渲染、动画、事件转发、导航、窗口布局 | 业务计算、直接访问 DAO/API、**自己做关系判断** |
| ViewModel | 状态管理、调用 UseCase、线程切换 | 持有 View/Context、写 SQL、算血缘 |
| UseCase | 业务规则、纯计算 | 依赖 Android 类、直接访问 DAO |
| Repository | 数据编排、Entity↔Domain 转换 | 业务规则判断 |
| DAO/API | 纯数据存取 | 任何业务逻辑 |

## 五、数据流（关键链路）

### 5.1 读数据：宠物首页

```
Room DAO (Flow<PetEntity>)
    ↓ 数据变化自动发射
PetRepositoryImpl
    ↓ map: Entity → Domain
ViewModel: Flow<Resource<Pet>> → StateFlow<HomeUiState>
    ↓
Fragment: collectInView { 更新 ViewBinding }
```

### 5.2 写数据：喂食互动

```
用户点击「喂食」
    ↓ Fragment: viewModel.feed(petId)
    ↓ ViewModel: launch { feedPetUseCase(petId) }
FeedPetUseCase:
    ├─ 校验冷却（业务规则）
    ├─ 校验/扣除道具
    ├─ 计算经验与亲密度（GrowthRules）
    ├─ 判断升级（LevelUpPetUseCase）
    └─ 持久化
    ↓ Room 写入 → Flow 发射 → UI 刷新
    ↓ 同时发布 DesktopEvent(FEED, targetPetId)
```

### 5.3 🆕 桌面事件-反应流（v2.0 核心链路）

```
① 用户拖动「爸爸」并松手 → 爸爸从高处落下
    ↓
PetGestureController: 识别为 THROW_DOWN 事件
    ↓
DesktopEventBusImpl.publish(
    DesktopEvent(action = THROW_DOWN, targetPetId = dad.id, intensity = 0.8f)
)
    ↓
② 订阅者：同屏所有其他宠物（爷爷、孩子）
    ↓
对每个 observer：
ResolveReactionUseCase(
    event = event,
    observer = grandpa
) → Reaction(
    renderState = PetRenderState.Upset,      // 状态机输入
    motion = Motion.TowardsTarget,           // 位移意图
    bubble = Bubble.Text("哎呀！"),           // 气泡
    priority = 2
)
    ↓
③ ReactionPlayer 播放：
    ├─ renderer.render(state)         → Rive 状态机切换
    ├─ 位移插值（扑过去）              → FloatingWindowManager 更新坐标
    └─ BubbleQueue.enqueue(bubble)    → 气泡悬浮层显示
    ↓
④ 全体宠物反应完成 → 回到原状态
```

**关键设计**：`ResolveReactionUseCase` 是**纯函数**（输入 event + observer + 关系 → 输出 reaction），因此：

- 可以 100% 单元测试
- 反应表可以做成配置（`ReactionTable`），策划可直接改 JSON 而不改代码
- 新增宠物类型时不需要改事件总线

### 5.4 🆕 配对生育数据流

```
用户在配对广场选目标 → 邀请（真人）/ 立即（NPC）
    ↓
PairPetsUseCase(petA, petB)
    ├─ 校验：双方成年、不同主、冷却、公母、后代数
    ├─ 扣除金币
    ├─ NPC：立即生成 Pairing(ACCEPTED)
    └─ 真人：生成 Pairing(PENDING)，等待对方响应
    ↓ 接受后
BreedPetUseCase(pairing)
    ├─ 基因混合 + 变异（PetGenes.inherit）
    ├─ 稀有度漂移判定（BreedingRules.offspringRarity，基准 = max(父母)，永不降级）
    ├─ 物种判定（BreedingRules.offspringSpecies，按 PairingKind 分档）
    ├─ 世代 = max(genA, genB) + 1
    ├─ 生成 2 只后代（A 方 1 只、B 方 1 只）
    └─ 各自写入本地 → 云端同步
    ↓
族谱服务重建 FamilyGraph（增量更新边）
```

## 六、宠物渲染层设计（核心）

### 6.1 设计目标

1. **可插拔**：业务层不关心 Rive / Lottie / 帧动画
2. **可降级**：低端机自动降级
3. **可远程切换**：不更新 App 就能换方案（灰度）
4. 🆕 **可多实例**：**桌面 ≤3 只**（= 系统悬浮窗数）/ **家 ≤6 只**（= 场景 View 树节点数），共享调度与资源池。
   三层链条（**拥有不限 ⊃ 家在册 6 ⊃ 桌面 3**，含包关系）见 [00 §4.1](./00-产品需求文档PRD.md) / [09 U-12](./09-待决问题总表.md)

### 6.2 契约定义

```kotlin
// core/domain/pet/PetRenderer.kt

interface PetRenderer {
    fun load(species: PetSpecies, stage: PetStage, genes: PetGenes)
    fun render(state: PetRenderState)
    fun supportsTouch(): Boolean
    fun setScale(scale: Float) {}
    fun setOpacity(alpha: Float) {}          // 🆕 景深（后排变暗）
    fun pause() {}
    fun resume() {}
    fun release()
}

interface PetRendererFactory {
    fun create(mode: RenderMode = RenderMode.current()): PetRenderer
}

enum class RenderMode { RIVE, LOTTIE, FRAME_ANIM, MODEL_3D }

// 🆕 多实例池：同一帧统一 tick，避免 N 个 View 各自 invalidate
interface PetRendererPool {
    fun acquire(): PetRenderer
    fun releaseToPool(renderer: PetRenderer)
    fun setForeground(foreground: Boolean)   // 前后台降帧
}
```

### 6.3 渲染状态全集（v2.0）

```kotlin
sealed interface PetRenderState {

    data class Dragging(val velocity: Float) : PetRenderState
    data object Thrown : PetRenderState
    data object Dizzy : PetRenderState          // 🆕 撞边缘晕眩
    // 行为
    data object Eating : PetRenderState
    data object Playing : PetRenderState
    data object Training : PetRenderState
```

### 6.6 🆕 多实例渲染策略（v2.0 关键）

**问题**：3 个 `RiveAnimationView` 各自独立 60fps 刷新 → CPU/GPU 三倍负载，中低端机必掉帧。

**方案对比**

| 方案 | 说明 | 结论 |
|------|------|------|
| A. N 个独立 View + N 个悬浮窗 | 实现简单 | ❌ 内存 & 帧率不可控 |
| B. **1 个全屏透明 View + N 个 Rive 节点** | 单窗口单 Canvas，统一 draw | ✅ **采用** |
| C. TextureView / SurfaceView 混用 | 性能好但复杂度高 | ⚠️ 备选 |

**采用方案 B 的实现要点**

```
PetFloatingService
  └─ 1 个全屏透明 RiveAnimationView（覆盖整个屏幕，FLAG_NOT_TOUCH_MODAL）
       ├─ Rive Node: pet_1  (位置 A, scale 1.0, alpha 1.0)
       ├─ Rive Node: pet_2  (位置 B, scale 0.9, alpha 0.9)
       └─ Rive Node: pet_3  (位置 C, scale 0.8, alpha 0.85)
```

**优点**

- **1 次 draw call 批次**：所有宠物在同一 Canvas 上绘制
- **统一帧调度**：一个 `Choreographer` 回调驱动所有节点，天然同步
- **触摸命中测试可控**：全屏 View 收到触摸 → 用坐标反查命中的是哪只宠（O(n)，n≤3）
- **场景级效果更容易**：想要"全体看向 A"只需遍历节点

**触摸命中测试**

```kotlin
// 全屏 View 的 onTouchEvent
override fun onTouchEvent(event: MotionEvent): Boolean {
    val hit = scene.hitTest(event.x, event.y)   // 从后往前遍历（上层优先）
    return hit?.let { petNode -> gestureController.dispatch(petNode, event) } ?: false
}
```

**返回键与穿透**：全屏透明窗口会拦截点击。因此：

- 窗口使用 `FLAG_NOT_FOCUSABLE`（不抢焦点）
- 用 `FLAG_NOT_TOUCH_MODAL` + 精确的命中测试区域
- **只在宠物真正占据的矩形内**返回 `true` 消费触摸，其余返回 `false` 让事件穿透
- 若某 ROM 不支持事件穿透，降级为：**宠物各自一个独立小窗口**（方案 A），并在设置中提供开关

> ⚠️ **风险登记**：方案 B 的最大不确定性是"透明全屏窗口下的触摸穿透在不同厂商 ROM 上的行为"。Phase 4 必须先做**多机型真机验证**，并保留方案 A 的降级路径。

### 6.7 气泡层设计（🆕）

```
BubbleWindow（独立悬浮窗 或 场景内 View）
  ├─ 跟随目标宠物头顶锚点
  ├─ 队列化：同一时刻最多 1 条气泡（BubbleQueue）
  ├─ 生命周期：2.5s 自动消失，可被打断
  ├─ 优先级：事件反应气泡 > 随机搭话气泡
  └─ 防刷屏：同一宠物 5s 内不重复同类气泡
```

**为什么气泡独立成层**：Rive 内做文字气泡需要把文字"画"进矢量资源，多语言无法维护。独立 TextView 层天然支持中文、动态文案、字体缩放。

### 6.8 降级策略

```kotlin
override fun create(mode: RenderMode): PetRenderer = when {
    !DeviceCapability.canRunRive() -> FramePetRenderer()
    mode == RenderMode.RIVE -> RivePetRenderer()
```

**设备能力判断**：内存 < 2GB 或 API < 24 或 GPU 不支持时降级。

### 7.2 云端预留设计（v2.0：从"预留"升级为"刚需"）

**变化原因**：配对生育、族谱、串门**必须有服务端**才能真实运行（本地无法知道别人的宠物）。

| 预留点 | 实现方式 |

| 开关 | `BuildConfig.CLOUD_ENABLED` + `AppConfig.cloudEnabled` |
| 冲突策略 | **Last-Write-Wins**（按 `updatedAt`），后续升级字段级合并 |
| 待同步队列 | `PetDao.queryPendingSync(since)` |
| 🆕 匿名账号 | 首次启动即生成匿名 `ownerId`（本地 UUID），联网后升级绑定手机号 |

| 悬浮窗常驻内存增量（3 只） | < 80MB |
| 悬浮窗耗电 | 后台降帧至 15 FPS 或暂停 |
| 事件反应延迟 | < 100ms（从动作发生到其他宠物开始反应） |
| APK 体积 | < 40MB（含首期 .riv 资源） |
| 气泡弹出延迟 | < 50ms |

### 11.2 合规红线（技术侧）

| 要求 | 落实方式 |
|------|---------|
| 不使用无障碍服务 | **禁止**添加 `BIND_ACCESSIBILITY_SERVICE` 权限 |
| 不读取第三方 App | **禁止**引入 `AccessibilityService` / `MediaProjection`；**禁止** `QUERY_ALL_PACKAGES` |
| 不模拟操作第三方 App | **禁止**注入 `MotionEvent` 到其他窗口 |
| 网络全 HTTPS | `network_security_config` 已设 `cleartextTrafficPermitted="false"` |
| 不信任所有证书 | 使用系统默认校验，**禁止** `TrustAllCerts` |
| 隐私同意前不初始化 SDK | `SproutPetApplication.onPrivacyAgreed()` 统一入口 |
| 密钥不入库 | `keystore.properties` + `.gitignore` |
| 悬浮窗用途声明 | 隐私政策明确"桌面宠物展示" |
| 🆕 未成年人保护 | 实名认证 + 时长/消费限制（接入防沉迷 SDK） |
| 🆕 概率公示 | 盲盒、稀有度突变概率在游戏内可见 |

## 十二、技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Rive 美术资源制作周期长 | 阻塞 Phase 3 | Phase 1-2 用帧动画/属性动画占位，渲染抽象已就绪 |
| Rive 商用授权不明确 | 法务风险 | 提前确认 License；备选 Lottie（Apache 2.0） |
| 悬浮窗厂商 ROM 兼容性 | 部分机型不显示 | 复用 TemplateAPP 多厂商适配；Phase 4 真机矩阵验证 |
| ⚠️ **全屏透明窗口触摸穿透** | 部分 ROM 拦截全部点击 | **Phase 4 专项验证**；保留"独立小窗口"降级方案 |
| 多宠物渲染内存占用 | 低端机 OOM | 单 Canvas 多节点 + 共享资源池 + 低端机降为 1 只 |
| 无后端时社交受限 | 配对/族谱无法真实运行 | NPC 配对兜底；匿名账号 + 本地模拟 |
| 事件-反应组合爆炸 | 状态机资源量失控 | 用 `emotion` Number 通道 + Blend Tree，不按组合出资源 |
| 生育结果双方不一致 | 族谱失真 | ⭐ **生育在服务端生成并下发** |
| 数值失衡 | 留存下降 | 参数集中 `GrowthRules`，可热更新 |
| 桌宠被用户投诉"骚扰" | 差评/下架 | 气泡频次限制 + 一键静音 + 一键隐藏桌宠 |
