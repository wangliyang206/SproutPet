## 一、要解决的问题

### 1.1 现状（参考同类项目的教训）

传统做法是 `<animation-list>` 帧动画 + 固定尺寸 `ImageView`：

```xml
<!-- 问题所在：只有 2 张图循环，且容器尺寸固定 -->
<animation-list android:oneshot="false">
    <item android:drawable="@mipmap/chicken_blink_0" android:duration="2000" />
    <item android:drawable="@mipmap/chicken_blink_1" android:duration="300" />
</animation-list>

<ImageView android:layout_width="100dp" android:layout_height="100dp" />
```

**三个致命缺陷**

| 缺陷 | 后果 |
|------|------|
| 帧动画 = 切图轮播 | 无骨骼、无形变 → **不立体**，像贴纸 |
| 单一静态容器 | 无法做缩放/位移/旋转的组合运动 → **没有空间感** |
| 无触摸监听 | 点它、拖它、不理它表现一样 → **没有互动** |
| 每套动作 20~25 张 PNG × 5 分辨率 | APK 体积暴涨，新增宠物成本极高 → **只有 2 个模型** |

### 1.2 目标

| 目标 | 验收标准 |
|------|---------|
| 立体感 | 有骨骼形变（挤压/拉伸）、重心偏移、视差跟随 |
| 互动性 | 6 种手势有不同反馈；能感知 App 状态 |
| 资源效率 | 单宠物全套动作 < 1MB；新增宠物边际成本低 |
| 可降级 | 低端机自动降级，不崩溃 |
| 可替换 | 业务层零改动即可换渲染方案 |

## 二、方案选型

| 方案 | 立体感 | 互动 | 体积 | 开发成本 | 美术成本 | 结论 |
|------|-------|------|------|---------|---------|------|
| 帧动画（现状） | ⭐ | ⭐ | 差 | 极低 | 中 | 仅作降级 |
| **Rive** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 优 | 中 | 中 | ✅ **首选** |
| Lottie | ⭐⭐ | ⭐⭐ | 优 | 低 | 低 | 降级备选 |
| Live2D | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 中 | 高 | 高 | Q 版角色用不上 |
| 真 3D | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 差 | 高 | 高 | 仅应用内展柜 |

### 2.1 为什么选 Rive

**1. 立体感来自骨骼 + 网格变形**

Rive 支持把角色部件（头、身、翅、眼、脚）做成**骨骼层级 + 顶点权重网格**，可实现：

- 跳跃时的 **squash（压缩）→ stretch（拉伸）**
- 被拎起时身体纵向拉长、四肢下垂
- 转弯时重心倾斜、尾巴反向摆动

> 注意："立体"≠ 真 3D，而是"有体积感、会形变"。成本远低于真 3D，观感提升巨大。

**2. 互动能力是内建的 State Machine**

| | Lottie | Rive |
|---|--------|------|
| 本质 | 时间轴回放 | 实时状态机 |
| 互动 | 只能 play/pause/loop | 设置输入值，自动平滑过渡 |
| 代码 | 需手动编排多段动画衔接 | 只暴露 inputs，逻辑在美术侧 |

**3. 资源体积小**：`.riv` 矢量 + 压缩，全套动作 200KB~800KB，比几百张 PNG 小 1~2 个数量级。

**4. 跨平台**：同一份 `.riv` 可用于 Android / iOS / Flutter / Web，未来做 iOS 版零重复美术成本。

**5. 换装成本极低**：同一套骨骼换贴图即可，是"个性化装扮"玩法的天然载体。

### 2.2 Rive 的缺点（须提前知晓）

- 编辑器闭源，学习曲线中等（需理解 inputs / state machine 概念）
- 复杂骨骼绑定需专门美术，DIY 易出"关节反向"的劣质效果
- 中文教程较少，以官方文档为主
- **商用授权需确认**（见第六节）

### 2.3 资源组织策略（v2.1 新增 ⭐）

> 背景：物种从 6 种扩到 **18 种**（五虫体系，见 [07-五虫体系设计](./07-五虫体系设计.md)），稀有度从 5 档扩到 **6 档**（新增不可抽取的「灵兽」，见 [06-物种与稀有度设计](./06-物种与稀有度设计.md)）。
> 如果按"物种 × 稀有度 × 阶段"暴力出资源，将是 `18 × 6 × 5 = 540` 套，**美术必崩**。必须分层。

**核心原则：把「变化维度」和「不变维度」切开，能复用的绝不多做一份。**

| 维度 | 变化频率 | 实现方式 | 资源量 |
|------|---------|---------|--------|
| **物种** | 低（新增才变） | 独立 `.riv`：各物种专属骨骼比例 + 部件 | 18 套 |
| **成长阶段** | 中（4~5 段） | **同一 `.riv` 内的 State Machine 状态**，用骨骼缩放 + 部件显隐表达"幼→成" | 复用，+0 |
| **稀有度（1~5 档）** | 高（每个体不同） | **不换模型**！用**材质/特效层**：`rarity_tier` Number 输入 → 光效强度、粒子密度、描边颜色 | 复用，+0 |
| **稀有度（第 6 档 · 灵兽）** | 低但特殊 | 复用基础骨骼 + **异变层**：异色瞳 / 荧光 / 双色 / 变异体型 | 复用，+0 |
| **基因（花色）** | 最高（每个体唯一） | Rive **`color` 输入 + 部件替换**，换贴图不换骨骼 | 复用，+0 |
| **神兽形态** | 极低（稀有） | 复用基础骨骼 + **部件层/特效层**（额外翅膀/角/尾/光环） | **4 套**附加层（蠃虫不设，见 ADR-020） |

**结论：真正需要美术独立绘制的只有「18 个物种骨骼 + 4 套神兽附加层」，其余全部靠输入通道驱动。**

**Rive 输入通道约定（建议）**

```kotlin
// 渲染层只需把领域数据映射成这几个输入值
object RiveInputs {
    const val STAGE        = "stage"          // Number: 0..5 成长阶段
    const val GROWTH       = "growth"         // Number: 0..1 阶段内进度（用于平滑过渡）
    const val RARITY_TIER  = "rarity_tier"    // Number: 0..5 稀有度档位
    const val IS_MUTANT    = "is_mutant"      // Boolean: 是否灵兽（开启异变层）
    const val HAS_DEITY    = "has_deity"      // Boolean: 是否神兽形态（蠃虫恒为 false）
    const val DEITY_ID     = "deity_id"       // Number: 0..3 对应四种可具象的五虫之长
    const val BODY_COLOR   = "body_color"     // Color: 基因主色
    const val ACCENT_COLOR = "accent_color"   // Color: 基因辅色
    const val PATTERN      = "pattern"        // Number: 0..7 花色编号
    const val EMOTION      = "emotion"        // Number: 情绪通道（Phase 5 事件反应）
}
```

> ⚠️ **不要为稀有度出独立模型**。稀有度是"同一只宠物更闪/更贵"，不是"换了一只"。灵兽同理——它是**同一只物种发生异变**，不是新物种。这条原则直接决定了美术成本能否收敛。

**降级路径（必须实现）**

| 设备档位 | 表现 |
|---------|------|
| 高 | 完整 Rive + 稀有度特效层 + 神兽附加层 + 粒子 |

### 3.2 抽象层（已完成）

业务层只依赖 `PetRenderer` 接口（`core/domain/pet/PetRenderer.kt`）：

```kotlin
interface PetRenderer {
    fun load(species: PetSpecies, stage: PetStage, genes: PetGenes)
    fun render(state: PetRenderState)
    fun setScale(scale: Float) {}
    fun pause() {}
    fun resume() {}
    fun release()
}
```

**这样设计的好处**：
- Phase 1 用帧动画实现 → Phase 3 换 Rive 实现 → **上层代码零改动**
- 低端机自动降级
- 可通过远程配置灰度切换

### 3.3 Rive 实现（Phase 3 落地）

```kotlin
// app/pet/renderer/rive/RivePetRenderer.kt
class RivePetRenderer(
    private val view: RiveAnimationView
) : PetRenderer {

    private var stateMachine: RiveStateMachine? = null
    private var current: PetRenderState? = null

    override fun load(species: PetSpecies, stage: PetStage, genes: PetGenes) {
        val resId = PetAssetResolver.resolve(species, stage)
        view.setRiveResource(resId, stateMachineName = SM_NAME, autoplay = true)
        stateMachine = view.stateMachines.firstOrNull()

        // 基因 → 渲染参数：让每只宠物长得都不一样
        stateMachine?.apply {
            setNumber("geneBodySize", genes.bodySize)
            setNumber("geneHueShift", genes.hueShift)
            setNumber("genePatternDensity", genes.patternDensity)
            setNumber("geneEyeSize", genes.eyeSize)
            setNumber("geneTailLength", genes.tailLength)
            setNumber("liveliness", genes.liveliness)
        }
    }

    override fun render(state: PetRenderState) {
        if (state == current) return          // 幂等保护，避免打断动画
        current = state
        val sm = stateMachine ?: return
        when (state) {
            is PetRenderState.Idle       -> sm.setBoolean("isIdle", true)
            is PetRenderState.Petted     -> sm.fire("tap")
            is PetRenderState.Excited    -> sm.fire("doubleTap")
            is PetRenderState.Grabbed    -> sm.fire("grab")
            is PetRenderState.Eating     -> sm.fire("eat")
            is PetRenderState.Playing    -> sm.fire("play")
            is PetRenderState.Training   -> sm.fire("train")
            is PetRenderState.Tired      -> sm.setBoolean("isTired", true)
            is PetRenderState.Sleepy     -> sm.setBoolean("isSleepy", true)
            is PetRenderState.Sleeping   -> sm.setBoolean("isSleeping", true)
            is PetRenderState.LevelUp    -> sm.fire("levelUp")
            is PetRenderState.Focusing   -> sm.setBoolean("isFocusing", true)
            is PetRenderState.Marrying   -> sm.fire("marry")
            is PetRenderState.Upset      -> sm.setBoolean("isUpset", true)
            is PetRenderState.Incubating -> sm.setNumber("hatchProgress", state.progress)
            is PetRenderState.Hatching   -> sm.setNumber("hatchProgress", state.progress)
            is PetRenderState.Dragging   -> {
                sm.setNumber("dragX", state.offsetX)
                sm.setNumber("dragY", state.offsetY)
                sm.setBoolean("isDragging", true)
            }
        }
    }

    override fun pause()  { view.pause() }
    override fun resume() { view.play() }
    override fun release() { stateMachine = null; view.stop() }

    private companion object { const val SM_NAME = "MainStateMachine" }
}
```

### 3.5 桌宠窗口架构（⭐ v1.3 新增 · 已真机验证）

> 依据：ADR-025，实测记录见 [99-桌宠技术验证操作单](./99-桌宠技术验证操作单.md) §六（Xiaomi Mi 9 Pro 5G / Android 11，2026-10-16）。
> 本文档的 §3.1~§3.4 讲的是**怎么画宠物**；本节讲的是**宠物怎么站到桌面上**（窗口层）。

#### 3.5.1 问题：Android 的触摸是**窗口级**的

没有"某个窗口只有部分区域可穿透"的 API。全屏窗口只有两种命运：

| 设置 | 结果 |
|------|------|
| 加 `FLAG_NOT_TOUCHABLE` | 整个窗口不收触摸 → 全穿透 → **宠物点不动** |
| 不加 | 整个窗口收触摸 → **整个桌面点不动** |

#### 3.5.2 方案：渲染与触摸**分层**

```
┌─ 渲染层：1 个全屏窗口（N 个宠物节点画在同一张画布上）
│    type   = TYPE_APPLICATION_OVERLAY
│    size   = MATCH_PARENT × MATCH_PARENT
│    flags  = FLAG_NOT_TOUCHABLE | FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_NO_LIMITS
│    format = TRANSLUCENT
│    ⚠️ 只画不收 —— 这是"不挡桌面"的框架级保证
│
└─ 触摸层：N 个宠物大小的窗口（每只宠物一个）
     type   = TYPE_APPLICATION_OVERLAY
     size   = petSize × petSize（建议四周各留 24dp 余量，见 3.5.4）
     flags  = FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_NO_LIMITS
     format = TRANSLUCENT，**不画任何东西**
     ⚠️ 只收不画 —— 每个窗口随对应宠物一起移动
```

**窗口总数 = 1 + N**（3 只宠物 = 4 个窗口）。触摸层是纯透明的，开销远低于一个渲染窗。

> ⚠️ **这里的 N = 手机桌面上的只数，上限 3**（三层链条见 [00 §4.1](./00-产品需求文档PRD.md)）。
> App 内的「家」**不用这套窗口方案** —— 家在自家 View 树里，**在册上限 6 只**，是节点不是窗口。

#### 3.5.3 为什么不用「每宠一个渲染窗」

一个反直觉但决定性的原因：**每只宠物一个独立窗口，跨宠物动画在物理上不可能**。

「一家三口」是本产品的核心卖点，它天然包含**跨越两只宠物**的画面：

- 两只宠物互相蹭头、并排坐下
- 心形 / 星星粒子从 A 飘到 B
- 桌面天气（雨、雪、落叶）落在所有宠物上
- 一起睡觉时共用的"梦泡泡"

这些都需要**同一张画布**。独立窗口方案里，它们会被各自的窗口边界直接裁掉。
若为了补回效果再加一个全屏特效窗，就退化成"1 渲染窗 + N 渲染窗"，严格劣于本方案。

次要原因：ADR-014 的原始意图（单渲染面、N 个 Rive 节点、统一帧调度、单实例纹理）
只在"1 个渲染窗"时成立。

#### 3.5.4 三条必须遵守的实现约束（都来自实测踩坑）

| # | 约束 | 为什么 |
|---|------|--------|
| 1 | **位置必须钳制到屏幕内**：`x ∈ [0, screenW - petSize]`、`y ∈ [0, screenH - petSize]` | 实测出现过宠物被拖到 `x = -215`（左边缘外 215px）和 `x = 960`（屏宽 1080 时超出 182px），**跑出去就找不回来了** |
| 2 | **拖动判定用累计位移 + `ViewConfiguration` 的 touch slop，一旦开始拖动就按每帧位移跟手** | ❌ 反例：每次 `ACTION_MOVE` 重置基准点、要求单帧位移 ≥ 6px —— 6px/帧 ≈ 360px/秒，**慢速拖动每帧位移不足 6px，会被整段丢弃，宠物纹丝不动**，松手还被误判为点击 |
| 3 | **触摸事件一律用 `event.rawX / rawY`（屏幕坐标），不能用 `event.x / y`** | 触摸窗会**跟着宠物移动**，局部坐标在手指下方不断跳变；用局部坐标会导致位移自我累积、宠物"飞走" |

> ⚠️ **约束 1 的副作用（务必提前处理）**：宠物被钳制在屏幕边缘后，手指还能继续往外滑
> → 手指离开触摸窗 → 收到 `ACTION_CANCEL` → 拖动被系统中断。
> **推荐做法：触摸窗四周各留 24dp 余量**，让手指滑到屏幕边缘时仍在窗内。

**这三条约束已固化为可测代码**（放在 `core` 而非 `app`，因为它不依赖 `WindowManager`，可单元测试）：

| 代码 | 作用 |
|------|------|
| `core/domain/desktop/DesktopPetLayout.clamp()` | 位置钳制（含"屏幕比宠物还小"的退化处理） |
| `DesktopPetLayout.touchWindowSize() / isInTouchWindow()` | 触摸窗比宠物大一圈的余量圈 |
| `core/domain/desktop/DragGestureTracker` | 累计位移过 touch slop 判定拖动，之后按每帧位移跟手 |
| `core/src/test/.../DesktopPetLayoutTest.kt` | **18 例**守护，含慢拖回归测试（每帧 2px × 100 帧） |

> 📌 app 侧接入（`PetFloatingService` 由骨架转为实现）时，直接复用以上逻辑，
> `touchSlopPx` 传 `ViewConfiguration.get(context).scaledTouchSlop`。

#### 3.5.5 已知代价与待补测项

| 项 | 说明 |
|----|------|
| 触摸窗四角是死区 | 方形窗口里套圆形宠物，约 21% 面积是"点了没反应、也点不到桌面"的灰色地带。暂可接受，后续可评估收紧窗口尺寸 |
| 全屏透明窗的内存 | `MATCH_PARENT` 的 TRANSLUCENT 缓冲（1080×2340 约 10MB），且只在内容变化时重新合成 |
| **3 只宠物同屏未实测** | 3 个触摸窗互不干扰、窗口层级、渲染性能均待验证 |
| **仅小米 ROM 通过** | 华为 / 荣耀、OPPO / vivo 仍是空白，不能宣布"全机型可用" |

### 4.3.1 稀有度与形态输入（⭐ v2.1 新增）

> **重要**：稀有度**不换模型**，神兽形态**不重做骨骼**。全部靠输入通道驱动。
> 详见 §2.3 资源组织策略。

| 输入名 | 类型 | 范围 | 影响 |
|--------|------|------|------|
| `rarityTier` | Number | 0~5 | 光效强度 / 描边颜色档位（5=灵兽） |
| `isMutant` | Boolean | — | ⭐ 开启**异变层**（异色瞳 / 荧光 / 双色 / 变异体型） |
| `hasDeity` | Boolean | — | ⭐ 开启**完整神兽附加层**（ADR-026 起改由"灵兽 × 同虫"决定） |
| `hasDeityFeatures` | Boolean | — | ⭐ 开启**神兽特征层**（部分特征），稀有度 ≥ 传说即为真 |
| `deityId` | Number | 0~3 | **`0=蛟龙 1=麒麟 2=凤凰 3=神龟`**（与 `SpeciesFamily.deityId` 严格一致；**蠃虫与不入十类恒不传此值**，见 ADR-020 / ADR-026） |

> ⚠️ **两个通道的取值来源不同，别接错**（ADR-026）：
> - `hasDeityFeatures` ← `rarity.id >= LEGENDARY.id`（**抽卡回报**，纯数值推导）
> - `hasDeity` ← `Pet.hasFullDeityForm`（**出生时结算并持久化**，因为需要"诞生时的配对类型"）
>
> 三个布尔通道互不包含：**跨虫灵兽可以 `hasDeityFeatures = true` 而 `hasDeity = false`** ——
> 这对应"它有神兽特征层，但没有完整形态层"。美术需按这个组合出效果，不要当成异常。

#### 4.3.1.1 ⭐ 图层叠加顺序（**必须按此实现**，U-08）

> 此前只定义了三个通道的**取值来源**，却没定义它们**同时为真时谁盖谁** ——
> 美术各自发挥会导致同一只宠在不同界面长得不一样。以下是定稿。

**从底到顶的固定顺序**（`z` 为该层的渲染序号，数值仅用于表达相对次序）：

| z | 图层 | 开启条件 | 内容 |
|--:|------|---------|------|
| 10 | **基础体型层** | 恒开 | 骨骼 + 基因（体型/色相/花纹/眼睛/尾巴）+ 待机动作 |
| 20 | **稀有度特效层** | 恒开（按 `rarityTier` 递进） | 描边(1) → 光效(2) → 粒子(3) → 全套+专属动画(4) |
| 30 | **异变层** | `isMutant` | 异色瞳 / 荧光 / 双色 / 变异体型 |
| 40 | **神兽特征层** | `hasDeityFeatures` | 翎羽描边 / 龟甲刻纹 / 独角鳞纹（**部分**特征） |
| 50 | **完整神兽形态层** | `hasDeity` | 凤羽+尾翎 / 独角+鳞纹+瑞光 / 长须+龙角 / 龟甲刻纹+发光背甲 |

**三条叠加规则**

1. **恒为加法，永不替换模型** —— 任何一层都只在基础骨骼上叠部件/材质/特效，
   不切换 Rive 状态机（见 §2.3 资源组织策略）。
2. **`hasDeity = true` 时，「特征层」并入「完整形态层」，不重复绘制。**
   因为完整形态**本身已经包含**该虫的特征（凤羽里就有翎羽描边）。
   再叠一层会造成描边加深一倍、颜色偏差 —— 这是最容易出错的一点。
3. **`hasDeity = false` 且 `hasDeityFeatures = true` 时，只画到 z=40** ——
   即"有神兽特征、没有完整形态"（跨虫灵兽、或传说/神话档）。

**通道组合的完备表**（只有这 5 种，出现别的组合即为 Bug）

| 场景 | `isMutant` | `hasDeityFeatures` | `hasDeity` | 实际绘制到 |
|------|:---------:|:-----------------:|:---------:|-----------|
| 普通/稀有/史诗 | ✗ | ✗ | ✗ | z=30 |
| 传说/神话（五虫） | ✗ | ✓ | ✗ | z=40 |
| 灵兽 · 蠃虫 或 不入十类 | ✓ | ✗ | ✗ | z=30 |
| 灵兽 · 跨虫 | ✓ | ✓ | ✗ | z=40 |
| **灵兽 · 同虫** | ✓ | ✓ | **✓** | **z=50**（特征层并入） |

> 📌 由 `DeityRules` 保证的两条蕴含关系（可用来 assert）：
> ① `hasDeity ⟹ isMutant`；② `hasDeity ⟹ hasDeityFeatures`。
> 因此"`isMutant=true, hasDeityFeatures=false` 且 `hasDeity=true`"这类组合**不可能出现**。
> `DeityRulesTest` 有断言守住这两条。

**设计意图**

- 稀有度是「**同一只宠物更闪/更贵**」，不是「换了一只」→ 高稀有度只加特效层
- 灵兽是「**同一只物种发生异变**」，不是新物种 → 复用骨骼，只叠异变层
- 神兽形态是「**五虫之长**」的具象化 → 复用基础骨骼 + 部件层（翅膀/角/尾/光环）
- 这样美术成本从"物种 × 稀有度 × 形态"的乘积爆炸，收敛为**加法**（18 骨骼 + 4 附加层）
- 📌 **"同一物种长得不一样"由基因通道负责**（§4.3 的 6 个基因输入），
  与形态层正交：形态管"骨架与部件"，基因管"个体差异"。两者可以自由组合。

### 5.2 资源解析器

```kotlin
// app/pet/renderer/PetAssetResolver.kt
object PetAssetResolver {

    fun resolve(species: PetSpecies, stage: PetStage): Int {
        val s = stage.name.lowercase()
        val fs = fallbackStage(stage).name.lowercase()

        // ① 物种精确 → ② 物种阶段回落
        ResourceLoader.drawable("${species.id}_$s")?.let { return it }
        ResourceLoader.drawable("${species.id}_$fs")?.let { return it }

        // ③ 类群回落 → ④ 类群阶段回落（⭐ v1.8 新增，L1 类群层）
        val fam = species.family.name.lowercase()
        ResourceLoader.drawable("${fam}_$s")?.let { return it }
        ResourceLoader.drawable("${fam}_$fs")?.let { return it }

        // ❌ 禁止回落为某个具体物种（旧版这里 return pet_sprout_chicken_baby）
        throw MissingPetAssetException(species, stage)   // DEBUG 直接抛
    }

    /** 阶段资源复用规则：长者沿用成年模型 */
    private fun fallbackStage(stage: PetStage): PetStage = when (stage) {
        PetStage.ELDER, PetStage.RETIRED -> PetStage.ADULT
        PetStage.HATCHING -> PetStage.BABY
        else -> PetStage.BABY
    }
}
```

**好处**：美术未交付长者资源时自动复用成年模型，**不阻塞开发**；未交付某个物种时回落到**同族群的通用造型**，而不是回落成「某一隻碰巧先做好的物种」。

> ⛔ **v1.8 硬规则（体验回流后立）**
> | # | 规则 | 起因 |
> |---|------|------|
> | R-1 | **禁止回落到具体物种**（旧代码 `return pet_sprout_chicken_baby` 已删） | 这是「抽到 18 种全是鸡」的直接原因 |
> | R-2 | **资源缺失必须可见** —— DEBUG 抛 `MissingPetAssetException`；RELEASE 画醒目占位（红叉 + 物种 ID）并上报埋点 | 静默回落让缺陷**永不可见**，于是长期存在 |
> | R-3 | **取图必须传 `species`** —— `FramePetRenderer.drawableOf(stage)` 的签名本身就是缺陷，需改为 `drawableOf(species, stage)` | 只传 stage 时，species 形同虚设 |
>
> 完整交付分层（L1 类群层 / L1.5 物种配件层 / L2 物种独立造型）见 [15 §一](./15-宠物形象规范.md)。

## 八、Phase 1 过渡方案（Rive 资源未就绪时）

**不要因为等美术而停工**。先做"增强版帧动画 + 属性动画"，实现基本互动：

```kotlin
class FramePetRenderer(private val imageView: ImageView) : PetRenderer {

    override fun render(state: PetRenderState) {
        when (state) {
            is PetRenderState.Petted -> {
                imageView.setImageResource(R.drawable.pet_happy)
                bounce()                       // 属性动画：跳跃 + 挤压回弹
            }
            is PetRenderState.Grabbed -> {
                imageView.setImageResource(R.drawable.pet_grabbed)
                stretchVertically()            // 纵向拉伸模拟"被拎起"
            }
            is PetRenderState.Sleeping -> imageView.setImageResource(R.drawable.pet_sleep)
            else -> imageView.setImageResource(R.drawable.pet_idle)
        }
    }

    /** 挤压回弹：立体感的关键 */
    private fun bounce() {
        imageView.animate().scaleX(1.15f).scaleY(0.88f).setDuration(110)
            .withEndAction {
                imageView.animate().scaleX(0.95f).scaleY(1.06f).setDuration(140)
                    .withEndAction {
                        imageView.animate().scaleX(1f).scaleY(1f).setDuration(100).start()
                    }.start()
            }.start()
    }

    private fun stretchVertically() {
        imageView.animate().scaleX(0.82f).scaleY(1.35f).setDuration(160).start()
    }
}
```

**这只鸟也能"活"**：配合随机待机定时器 + 触摸监听，体验已远超现状。

> ⚠️ **2026-10-17 体验回流**：这套占位**只覆盖萌芽鸡一个物种**，`FramePetRenderer` 也只按 `stage` 取图 —— 结果是**抽到 18 种里的任何一种都显示为鸡**。此占位层（L0）已由 [15 §一](./15-宠物形象规范.md) **判定废除**，过渡期的最低要求是 **L1 类群层（6 × 3 = 18 个形态）**，不是「再多做一个物种」。

> 📌 **占位资源已交付（2026-10-16）**：上图 `pet_idle / pet_happy / pet_grabbed / pet_sleep`
> 是示意写法；实际命名遵循 §5.1 的 `pet_{speciesId}_{stage}` 规则，萌芽鸡为
> `pet_sprout_chicken_{baby|juvenile|adult|elder|happy|grabbed|sleep}` 与 `pet_egg_{common|cracked}`，
> 由 `tools/gen_pet_placeholder_vectors.py` 生成，预览见 `docs/art/sprout-chicken-preview.html`。

### 10.0 冷启动首帧：windowBackground 就是场景的第一帧（⭐ v1.12 · 2026-10-22）

**症状**：真机「第一次进入程序后，会闪一下」。

**根因**：`Theme.SproutPet.Splash` 的 `windowBackground` 是 `@color/bg_page`（**#F7F8FA，近白**），
而场景背景 `bg_home_day.png` 是「灰蓝天空 → 黄绿草地 → 深绿地面」的整屏图。
背景图解码完成的那一帧，整屏从近白跳成彩色 —— 那不是"加载慢"，是**首帧颜色不对**。
夜间更糟：先白闪、再切深蓝。

**定稿**：

| 项 | 规格 |
|----|------|
| 背景 | `bg_launch_day` / `bg_launch_night`（`<shape>` 三段线性渐变，**色值逐点采样自对应背景图**的顶/中/底） |
| 主题 | `Theme.SproutPet` 与 `Theme.SproutPet.Splash` 默认 `bg_launch_day`；`LaunchDay` / `LaunchNight` 两个变体只覆盖 `windowBackground` |
| 切换时机 | `MainActivity.onCreate` 在 **`super.onCreate` 之前** `setTheme(...)`（`DayNight.isNightNow()`），保证取到的是夜间/白天版 |
| 判据 | `core/domain/daynight/DayNight` —— 启动页、`SceneViewModel`、后续任何夜间逻辑**共用**；禁止各写一份 `hour >= 18` |
| 覆盖层 | 首蛋聚焦层从「瞬间出现」改 **220ms 淡入**（它是盖在场景上的第二层，突然出现同样算"闪"） |

> ⚠️ **不要用淡入动画掩盖跳色**：淡入只能把"白 → 场景"变成"白 → 渐显场景"，第一帧仍然是白的。
> 唯一有效的做法是**让第一帧本身就是场景的颜色**。

### 10.1 手势规范（对应 00 §4.2 · `design-v2/` 02/03 屏）

| 手势 | 触发 | 反馈 | 约束 |
|------|------|------|------|
| 单击 | 轻点宠物 | 弹跳 + 爱心涟漪 | 命中半径 ≥ 44dp（可访问性下限） |
| 长按 | ≥ 400ms | 档案浮卡从宠物身上浮起（08 屏） | 长按期间禁止触发其他手势 |
| 拖拽 | 按住宠物移动 | 「被拎起」形变（squash/stretch） | 释放回弹；拖到托盘道具上 = 喂食/玩耍（03 屏） |
| 快速甩出 | 高速拖拽后释放 | 抛物线飞出 + 撞边晕眩 | 仅装饰性负面反馈，**不扣数值**（守 ADR-021） |
| 双击空白 | 双击非宠物区域 | 宠物跑过来（召唤） | — |
| 连续快速点击 | 短时间 5 击 | 生气 / 冒星星，短暂拒绝互动 | 培养「宠物有脾气」，不惩罚数值 |

### 10.2 过渡规范（倒置 IA 下「没有页面，只有场景状态」）

> `U-10` 拍板倒置 IA 之后，**没有 Tab 页面跳转** —— 所有「切换」都是场景内的状态过渡。**四类**（v1.9 增第 4 类）：

| 过渡类型 | 用法 | 例子 |
|---------|------|------|
| **底部升起** | 半模态面板从底部滑入，场景仍在背景 | 开箱台（14 屏）· 孵化面板（05 屏）· 抽屉（09 屏） |
| **就地浮现** | 内容浮在触发它的对象上，跟随对象位置 | 档案浮卡（08 屏）· 气泡 · 揭晓卡（04 屏） |
| **走出边缘** | 宠物离开「家」的仪式性过渡 | 上桌「跳出去」（18 屏）· 隐居去后山小屋（27 屏 —— 全稿唯一离开「家」的场景）（00 §4.3） |
| **聚焦层**（v1.9 新增） | 一次性演出：场景压暗，唯一主角居中放大 | **首蛋孵化**（05 屏）—— 蛋 180dp 居中 · `MM:SS` 32sp 倒计时 · 呼吸/轻晃/数字跳动 · 敲击细纹；破壳后 200ms 淡出（[14 §1.4](./14-首日体验与孵化节奏.md)） |

**三条硬规则**：① 所有过渡 ≤ 300ms，**可被打断**（用户随时可点别处）；② **禁止「跳页」式全屏切换** —— 那是旧 IA 的肌肉记忆；③ 宠物**永远在场景里**，不允许出现「宠物不见了」的界面。

### 10.3 空态 / 错误态 / 兜底态

| 状态 | 规则 |
|------|------|
| **空态**（图鉴未收集 / 待命为空） | 「家」里永远至少有一只（首宠流程保证）；图鉴空态显示「第一只还没来」+ 指向抽蛋入口，**不放空白插画** |
| **错误态**（数据库 / 网络异常） | 宠物**继续活动**（渲染不依赖数据层）；错误用一句宠物台词表达：「我有点头晕，你重启一下我好吗？」—— **不弹系统错误框** |
| **权限拒绝**（悬浮窗） | 见 10.4 —— **拒绝 ≠ 失败**，是另一个正常分支 |
| **性能降级** | 按 §七 降级链执行；降级时宠物外观可变简，但**手势与位置不变** |

### 10.4 桌宠权限的拒绝兜底（⭐ `U-11` 第⑤条 · 定稿）

1. **拒绝授权不是错误** —— UI 上**没有任何红字 / 感叹号**；宠物只说一句：「那我先在家里陪你」。
2. **不反复弹**：同一次安装周期内，自动引导**最多 1 次**；此后入口只存在于抽屉「桌面宠物」（12 屏）。
3. **保留再次引导**：用户随时可从抽屉进入，重走 16 → 17 → 18 三屏（`design-v2/`）。
4. **部分授权**（给了悬浮窗但没给通知 / ROM 白名单）：桌宠可能被系统杀掉 —— 重启时宠物从桌面「回家」，并提示一次原因，**不判定用户操作错误**。
5. **关闭通知权限**：桌宠退回家中，数据无损。

## 十二、稀有度视觉分层（⭐ v1.17 新增 · 2026-10-22 用户需求）

> **用户原话**：「界面中怎么没有任何一个地方显示宠物稀有度呢？宠物普通、稀有、史诗、传说、神话、异兽，外形都一样吗？能不能改成不一样？」

### 12.1 问题定性（诚实回答）

- **稀有度是「个体」属性不是「物种」属性**：同一种萌芽鸡，可以抽出普通的、也可以抽（或融合/生育）出传说的（`BlindBoxEngine` 逐抽定档、`FusionRules` 融合上漂、`BreedingRules` 生育遗传）。所以**图鉴的物种格里没有稀有度可显示** —— 那是一格一个物种的口径。
- **此前确实所有稀有度外形完全一样**：`PetAssetResolver.resolve(species, stage)` 只认物种+阶段；`Rarity.fxDescription`（基础色→描边→光效→粒子→全套）从定义那天起**没有任何 UI 消费过它**。
- **稀有度此前只在三处出现过**：抽蛋揭晓卡（色字）、宠物档案卡、族谱行 —— 主场景 / 名册全无。

### 12.2 判据下沉：`Rarity.fxLevel`（core）

| 档位 | 稀有度 | fxLevel | 视觉（与 `fxDescription` 对齐） |
|------|--------|---------|--------------------------------|
| 0 | 普通 | 0 | 基础色：无光环，只有灰色脚标 |
| 1 | 稀有 | 1 | 描边档：微光晕（α60） |
| 2 | 史诗 | 2 | 光效档：光晕加亮（α105） |
| 3 | 传说 | 3 | 光效+粒子档：更亮更大（α150） |
| 4 | 神话 | 4 | 全套档：最亮最大（α190） |
| — | 灵兽 | 3 | 变异档：青色光晕（与传说同级，色相区分） |

> **判据在 core（`fxLevel` 数值），视觉在 UI**（`FramePetRenderer.applyRarityFx` 只做映射）——
> 与 A1「UI 只映射」红线同款纪律。

### 12.3 占位实现（Rive 未就绪阶段）

| 元素 | 实现 | 位置 |
|------|------|------|
| **稀有度脚标** | 槽位下方居中：稀有度色圆角底 + 白字（普通灰 / 稀有蓝 / 史诗紫 / 传说橙 / 神话红 / 灵兽青）—— 与 `BlindBoxRevealDialog` 的 rarity_* 色板同源 | `FramePetRenderer.rarityChip` |
| **稀有度光环** | 宠物身后径向渐变光晕，颜色 = 稀有度色，强度/外扩随 fxLevel 递增 | `FramePetRenderer.auraView` |
| **名册行** | 「Lv.N · 物种 · 类群 · **稀有度**」追加第四段 | `PetRosterDialog` |
| **场景槽位接入** | `PetRenderer.load()` 增 `rarity` 参数（接口默认 COMMON，两个调用点显式传 `pet.rarity`） | `SceneFragment` |

### 12.4 边界（什么**没有**做，为什么不）

| 没做的 | 为什么 |
|-------|--------|
| 图鉴物种格显示稀有度 | 物种口径下一格一个物种、稀有度属于个体 —— 没有单一值可显示；点格子进名册看个体时可见 |
| 粒子 / 专属动画（档 3~4） | 占位阶段无粒子系统；**Rive 美术到位后按同一 `fxLevel` 替换**（§5.1），视图层级与判据不动 |
| 悬浮窗（`FramePetRenderer` 复用处） | 自动继承同一光环与脚标，无需单独适配 |
