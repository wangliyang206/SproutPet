## 一、设计原则

1. **业务与存储解耦**：Entity 只负责持久化，业务行为在 Domain 层。转换由 Mapper 承担。
2. **枚举存 Int/String**：Room 不直接支持枚举，存 `id` 值，读取时用 `fromId()` 还原。
3. **冗余换性能**：高频排序字段（如 `power`）冗余存储，避免排行榜实时计算。
4. **为云端预留**：每张业务表都带 `remote_id` / `updated_at` / `is_synced`，Phase 6 接入后端时不改表结构。
5. **索引按查询建**：所有会出现在 `WHERE` / `ORDER BY` 的字段建索引。

## 二、ER 关系总览

```
┌──────────────┐
│     user     │  ← 用户（本地单用户时仅 1 条）
└──────┬───────┘
       │ 1:N
       ▼
┌──────────────┐        ┌──────────────┐
│     pet      │───N:M──│   pairing    │  ← 配对关系（宠物对宠物，无夫妻语义）
│  (宠物主体)   │        └──────────────┘
└──┬───┬───┬───┘
   │   │   │
   │   │   └──────────────┐
   │   │                  ▼
   │   │           ┌──────────────┐
   │   │           │  genealogy   │  ← 族谱（由 pet 的父母字段推导，不单独存表）
   │   │           └──────────────┘
   │   │
   │   └──1:N──► ┌──────────────────┐
   │             │  inventory_item  │  ← 背包
   │             └──────────────────┘
   │
   └──N:1──► ┌──────────────┐
             │    family    │  ← 家族
             └──────┬───────┘
                    │ 1:N
                    ▼
             ┌──────────────────┐
             │  family_member   │
             └──────────────────┘
```

> 说明：**族谱不单独建表**。族谱由 `pet.parent_id_a` / `pet.parent_id_b` + `generation` 动态构建树形结构。好处：不会出现"族谱表与实际父母关系不一致"的数据脏。

## 三、表结构详设

### 3.1 `pet` — 宠物主体表

**已实现（Phase 0）**，位于 `core/db/entity/PetEntity.kt`

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK, autoGenerate | 本地主键 |
| `owner_id` | INTEGER | INDEX | 主人用户 ID |
| `nickname` | TEXT | NOT NULL | 昵称（用户可改） |
| `species_id` | TEXT | NOT NULL | 种族 ID，对应 `PetSpecies.id` |
| `rarity` | INTEGER | NOT NULL | 稀有度 `0~5`（5=灵兽，**仅遗传产生，抽取池不会产出**） |
| `exotic_blood` | INTEGER | NOT NULL, DEFAULT 0 | **灵血浓度 `0~3`**（灵兽血统的隐性印记，见 06 §2.4） |
| `deity_form` | INTEGER | NOT NULL, DEFAULT 0 | **是否拥有完整神兽形态层**（`0/1`，ADR-026）。出生时由 `DeityRules.resolveAtBirth` 结算一次，此后不变 |
| `stage` | INTEGER | NOT NULL | 阶段 `0~6`（6=隐居 `RETIRED`） |
| `level` | INTEGER | NOT NULL | 等级 `0~60` |
| `exp` | INTEGER | NOT NULL | 当前经验 |
| `attr_stamina` | INTEGER | | 体力 |
| `attr_strength` | INTEGER | | 力量 |
| `attr_agility` | INTEGER | | 敏捷 |
| `attr_wisdom` | INTEGER | | 智慧 |
| `attr_charm` | INTEGER | | 魅力 |
| `attr_intimacy` | INTEGER | | 亲密度 `0~100` |
| `power` | INTEGER | INDEX DESC | **战力快照**（冗余，用于排序） |
| `gene_body_size` | REAL | | 基因-体型 `0~1` |
| `gene_hue_shift` | REAL | | 基因-色相 `0~1` |
| `gene_pattern_density` | REAL | | 基因-花纹密度 |
| `gene_eye_size` | REAL | | 基因-眼睛大小 |
| `gene_tail_length` | REAL | | 基因-尾巴长度 |
| `gene_liveliness` | REAL | | 基因-活泼度 |
| `born_at` | INTEGER | NOT NULL | 出生时间戳 |
| `hatch_at` | INTEGER | NOT NULL | 孵化完成时间戳 |
| `is_hatched` | INTEGER | NOT NULL | 是否已破壳 `0/1` |
| `spouse_id` | INTEGER | INDEX, NULL | 当前配对对象宠物 ID（v2.1 由 `spouse_id` 语义调整为"配对对象"） |
| `family_id` | INTEGER | INDEX, NULL | 所属家族 |
| `parent_id_a` | INTEGER | INDEX, NULL | 父/母 A |
| `parent_id_b` | INTEGER | INDEX, NULL | 父/母 B |
| `generation` | INTEGER | DEFAULT 1 | 世代数（根=1）。⭐ **v1.9：不再是"只存不算"** —— 由 `GrowthRules.GenerationRules.offspringGeneration = max(父, 母) + 1` 计算（修 `G-03`），领域模型 `Pet.generation` 是真相源 |
| `is_main` | INTEGER | DEFAULT 0 | **主宠**（恒占桌面 0 号）。全局至多 1 只，`HomeSlots.validate` 守住 |
| `home_slot` | INTEGER | DEFAULT -1 | 家在册槽位（0~5；**-1 = 待命**，非 NULL 哨兵）。家上限 6 = `HomeSlots.MAX_HOME_PETS` |
| `desktop_slot` | INTEGER | DEFAULT -1 | 桌面槽位（0~2；-1 = 未上桌）。含包约束：`desktop_slot != -1 ⇒ home_slot != -1` |
| `batch_no` | TEXT | NOT NULL | 盲盒批次号 |
| `is_retired` | INTEGER | DEFAULT 0 | 隐居标志（保留族谱数据）。⚠️ **真相源是 `PetStage.RETIRED`** —— 本列已降级为 **DAO 索引缓存列**，`Pet.isRetired` 是派生属性（`get() = stage == PetStage.RETIRED`），**不要再把它当独立状态写** |
| `remote_id` | TEXT | NULL | 服务端 ID |
| `updated_at` | INTEGER | NOT NULL | 最后修改时间 |
| `is_synced` | INTEGER | DEFAULT 0 | 是否已同步 |

**索引**

```sql
CREATE INDEX idx_pet_owner          ON pet(owner_id);
CREATE INDEX idx_pet_family         ON pet(family_id);
CREATE INDEX idx_pet_spouse         ON pet(spouse_id);
CREATE INDEX idx_pet_parent_a       ON pet(parent_id_a);
CREATE INDEX idx_pet_parent_b       ON pet(parent_id_b);
CREATE INDEX idx_pet_power          ON pet(power DESC);
CREATE INDEX idx_pet_hatch_owner    ON pet(is_hatched, owner_id);
```

**设计说明**

- `power` 冗余：排行榜需频繁按战力排序，实时计算 5 维加权开销大。每次属性变化时更新。
- `generation` 冗余：族谱查询时避免递归计算世代。**计算规则**：`offspringGeneration = max(父, 母) + 1`（`G-03` 修复：此前全代码无一处计算，恒为 1）。
- `is_retired` 而非物理删除：隐居宠物的数据要保留用于族谱，`is_retired=1` 不出现在常规列表。
  ⚠️ **本列不是真相源** —— `stage = RETIRED` 才是。本列只为"隐居宠过滤"这类查询提供索引，
  与 `stage` 在同一次写入里更新（`PetMapper` 负责）；**不要用它反推 `stage`**。

### 3.6 `pairing` — 配对表（Phase 6）

> ⚠️ **v2.1 变更**：v1.0 的 `marriage` 表改名为 `pairing`，语义从"婚姻"改为"**配对生育**"（见 ADR-008）。
> 无"夫妻"概念、无离异/丧偶状态；配对是可解绑的**繁殖关系**。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | INTEGER | PK | |
| `pet_id_a` | INTEGER | INDEX | 宠物 A（存较小 ID） |
| `pet_id_b` | INTEGER | INDEX | 宠物 B |
| `owner_id_a` | INTEGER | | A 的主人 |
| `owner_id_b` | INTEGER | | B 的主人 |
| `partner_is_npc_a` | INTEGER | DEFAULT 0 | A 的搭档是否为 NPC（`0/1`） |
| `partner_is_npc_b` | INTEGER | DEFAULT 0 | B 的搭档是否为 NPC |
| `is_same_owner` | INTEGER | DEFAULT 0 | 是否同一主人的两只宠物自配对（`0/1`） |
| `affection` | INTEGER | DEFAULT 0 | 双方好感度（亲密值 `0~100`） |
| `paired_at` | INTEGER | NOT NULL | 配对生效时间 |
| `last_breed_at` | INTEGER | DEFAULT 0 | 上次生育时间（冷却计算） |
| `offspring_count` | INTEGER | DEFAULT 0 | 已生育数量（上限 5） |
| `expire_at` | INTEGER | DEFAULT 0 | 邀请过期时间（真人配对未确认时，`paired_at + 3 天`） |
| `status` | INTEGER | DEFAULT 0 | `PairingStatus`：`0=PENDING 1=PAIRED 2=RELEASED 3=EXPIRED` |
| `updated_at` | INTEGER | | |
| `is_synced` | INTEGER | DEFAULT 0 | |

**唯一约束**：`UNIQUE(pet_id_a, pet_id_b)` —— 防止重复配对记录。

**索引**

```sql
CREATE INDEX idx_pairing_pet_a    ON pairing(pet_id_a);
CREATE INDEX idx_pairing_pet_b    ON pairing(pet_id_b);
CREATE INDEX idx_pairing_status   ON pairing(status);   -- 用于快速筛 PENDING 邀请
```

**设计说明**

- 存 `owner_id_a` / `owner_id_b` 是为支持**跨用户配对**（两个真实用户的宠物配对）。
- `partner_is_npc_*` 是 v2.1 新增：落实 ADR-011 —— **真人配对照走 `PENDING` 需对方确认；NPC 配对直接落 `PAIRED` 免确认**。查询待处理邀请只需 `WHERE status = 0`。
- `is_same_owner` 用于区分"同主人自配对"（本地即可完成）与"跨用户配对"（需同步）。
- `status` 不再有"离异/丧偶"：配对是轻量关系，解绑即 `RELEASED`，宠物归属**永不变更**。
- ⚠️ **历史数据迁移**（**迁移动机待确认**）：若本地已存在旧 `marriage` 表数据，`marriage` → `pairing` 时 `status` 的 `1`(离异)/`2`(丧偶) 统一映射为 `2`(RELEASED)；`spouse_id` 保留但语义变为"配对对象"。
  > 📌 此处**刻意不写版号** —— 早期版本写作"V6"，但那只是已被推翻的"计划版号"（见 §5.1 说明）。`pairing` 表落地时，版号以那时的 `DB_VERSION` 为准。

## 四、TypeConverter

Room 需要转换的非基础类型：

```kotlin
class Converters {

    @TypeConverter
    fun fromPetStage(stage: PetStage): Int = stage.id

    @TypeConverter
    fun toPetStage(id: Int): PetStage = PetStage.fromId(id)

    @TypeConverter
    fun fromRarity(rarity: Rarity): Int = rarity.id

    @TypeConverter
    fun toRarity(id: Int): Rarity = Rarity.fromId(id)

    @TypeConverter
    fun fromSpecies(species: PetSpecies): String = species.id

    @TypeConverter
    fun toSpecies(id: String): PetSpecies = PetSpecies.fromId(id)
}
```

> 💡 当前 `PetEntity` 直接存 `Int`/`String`（不用 Converter），是为了让实体更"扁平"、便于 SQL 直接查询。Converter 主要用于未来可能出现的复杂类型。

### 4.2 枚举 ID 映射表（v2.1 更新 ⭐）

> **这是数据库与领域模型之间的契约**。改动任何一方的 ID 都必须同步本表 + Migration，否则历史数据会错读。

**`rarity` 字段（0~5）** —— 见 `Rarity.kt`

| id | 名称 | 可抽取 | 说明 |
|----|------|-------|------|
| 0 | 普通 | ✅ | |
| 1 | 稀有 | ✅ | |
| 2 | 史诗 | ✅ | |
| 3 | 传说 | ✅ | |
| 4 | 神话 | ✅ | |
| **5** | **灵兽** | ❌ | **v2.1 新增。仅由 `BreedingRules` 遗传产生** |

> ⚠️ **历史数据不应出现 `rarity=5`**。若在线上数据中发现 `rarity=5` 但 `parent_id_a` 为空，说明有抽取路径绕过了 `Rarity.drawableEntries()`，是 **P0 Bug**。

**`exotic_blood` 字段（0~3）** —— v1.2 新增，见 `GrowthRules.ExoticBloodRules`

| 值 | 含义 |
|----|------|
| 0 | 无灵血 |
| 1~3 | **灵兽血统的隐性印记**，浓度越高，隔代觉醒回灵兽的概率越大（3% / 8% / 15%） |

> 💡 这是**纯派生字段**：由父母灵血与后代最终稀有度推导，**不参与属性计算**（守住 ADR-021）。
> 灵兽本身存 `MAX_BLOOD`（3）；非灵兽后代逐代 −1，三代归零。
>
> ⚠️ 它属于**稀有度轴**，与物种轴的「异兽」（`UNCATEGORIZED`）没有任何关系，不要混用同一张表字段去表达两件事。

**`deity_form` 字段（0/1）** —— v1.4 新增，见 `DeityRules`

| 值 | 含义 |
|----|------|
| 0 | 无完整神兽形态层（默认；**存量宠物全部落在这里**） |
| 1 | 拥有完整形态层（凤凰 / 麒麟 / 蛟龙 / 神龟）—— 由「**灵兽 × 同虫**」诞生（ADR-026） |

> ⚠️ **为什么它必须落库、而不能在渲染时现算**：
> 判定需要"**诞生时的配对类型**"这个信息，而宠物自身已经推不出来了
> （`parentIdA/B` 只指向父母本身，无法反推当时是"同虫"还是"跨虫"）。
> 所以它是**出生时结算一次、此后永不改变的个体特征**，与 `exotic_blood` 同性质。
>
> 📌 **迁移不丢数据**：V3 之前形态是**由稀有度现算的**，并没有"个体级形态"这个概念。
> 存量宠物升级后按新规则重新着色 —— 这是**规则的统一**，
> 而形态本来就是可推导的外观、不是玩家资产，所以不存在"数据丢失"。
>
> ⚠️ 它是**外观字段，不参与任何数值计算**（与 `exotic_blood` 同一条红线，ADR-021）。

**`gender` 字段（0/1）** —— v1.5 新增（V4 迁移），见 `PetGender.kt`

| 值 | 含义 |
|----|------|
| 0 | 公（`MALE`） |
| 1 | 母（`FEMALE`） |

> ⚠️ **这两个整数不可重排** —— 重排会让存量宠物整体变性。
> 判定入口是 `PairingRules.gendersCompatible`，不是各处自己比大小。
>
> ⚠️ **存量数据是迁移时随机分配的**（`UPDATE pet SET gender = (RANDOM() & 1)`），
> 不是统一给 0。统一给"公"会造成**不可逆死局**：老玩家的宠物从此再也配不上对
> —— 而用户无法自行改性别（PRD §十三 Q6）。随机分配与"开蛋时随机"的既定语义一致。
>
> 📌 它是**出生即定、永不改变**的字段，因此必须落库。不落库会出现
> "同一只宠时而能配、时而不能配"。这与 `exotic_blood` 的事故同源。

**`stage` 字段（0~6）** —— 见 `PetStage.kt`

| id | 名称 | 枚举 | 是否在桌面 |
|----|------|------|-----------|
| 0 | 蛋 | `EGG` | ❌ |
| 1 | **破壳中** | `HATCHING` | ❌ |
| 2 | 幼崽 | `BABY` | ✅ |
| 3 | 少年 | `JUVENILE` | ✅ |
| 4 | 成年 | `ADULT` | ✅ |
| 5 | 长者 | `ELDER` | ✅ |
| 6 | 隐居 | `RETIRED` | ❌ |

> ⚠️ **本表曾整体错位**（漏了 `HATCHING`，导致 1~6 全部串位，还多出一个不存在的"4 成熟"）。
> 它自称"数据库与领域模型之间的契约"，错位会让历史数据被系统性错读。
> 现以 `PetStage` 的 `id` 为唯一基准，两侧必须一致。
>
> 📌 `HATCHING`（id=1）当前**没有任何代码会进入它** —— `stageOf(level)` 永不返回它，
> `BlindBoxEngine.hatch()` 直接 `EGG → BABY`。它是"3 秒破壳过渡"的残留值，
> **去留待定**（见 `docs/09` D-02）。在决定之前，本表如实反映枚举现状。
>
> 💡 `isOnDesktop = isHatched && this != RETIRED`，而 `isHatched = this >= BABY`。
> 所以**幼崽就已经在桌面上**（不是"少年才上桌"）—— 这是"首日就要见到宠物"的落地方式。

**`species_id` 字段（TEXT）** —— 共 18 种 / 6 类群，见 [07-五虫体系设计](./07-五虫体系设计.md)

| 类群 | 枚举 | 物种数 | 示例 id |
|------|------|-------|---------|
| 蠃虫 | `LUO` | 3 | `SNAIL` / `BUBBLE_FROG` / `SOFT_OCTOPUS` |
| 鳞虫 | `LIN` | 3 | `KOI` / `GRASS_SNAKE` / `LITTLE_DRAGON` |
| 毛虫 | `MAO` | 3 | `SLEEPY_CAT` / `FLUFF_DOG` / `SWIFT_CAT` |
| 羽虫 | `YU` | 3 | `SPROUT_CHICKEN` / `VIGOR_CHICKEN` / `SCHOLAR_CHICKEN` |
| 昆虫 | `KUN` | 3 | `HONEY_BEE` / `SHELL_TURTLE` / `GLOW_BUG` |
| **不入十类** | `UNCATEGORIZED` | 3 | `STAR_FOX` / `MOON_RABBIT` / `GLOW_JELLY` |

> ⚠️ **`species_id` 存的是物种 id 字符串（如 `SNAIL`），不是类群**。类群由 `PetSpecies.fromId(species_id).family` 派生，**不落库**，避免双重真相源。

**`SpeciesFamily` 历史名称迁移映射**

早期版本类群名为 `BIRD`/`MAMMAL`/`OVINE`/`FELINE`/`EXOTIC`。若历史数据的 TEXT 字段中存过这些值，读取时通过 `SpeciesFamily.fromName()` 映射：

| 历史值 | 现行枚举 |
|--------|---------|
| `BIRD` / `禽类` | `YU` |
| `MAMMAL` / `兽类` / `OVINE` / `羊类` / `FELINE` / `猫科` | `MAO` |
| `EXOTIC` / `异种` | `UNCATEGORIZED` |

> ⚠️ **反向红线**：`SpeciesFamily` 枚举本体**只有 6 个值**。历史别名**只存在于 `fromName()` 字符串映射中**，绝不可是枚举常量。原因：枚举常量是**独立条目**不是别名，混入后会污染 `entries`，导致任何遍历类群的 UI 出现幽灵项。`PetSpeciesTest` 有测试守住这一点。

### 5.1.1 V8：为什么「回填数据」也算迁移

> ⚠️ 本文件开头写着「迁移只做加列/加表/加索引，不改已有列语义」。V8 是**唯一豁免**，
> 且必须同时满足三条，否则不许这么干：

| 前提 | V8 是否满足 |
|------|-------------|
| ① 该字段**此前从未被有效写入**（写入侧有 bug，不是用户在选） | ✅ 破壳与造蛋都走默认值 `-1`，只有 V5 迁移给最老一只写过 0 |
| ② 回填算法**确定性、可复算**，不依赖运气或设备 | ✅ 按 `id` 升序（= 出生先后）填 0..5，同一份数据永远同一结果 |
| ③ 注释写清**为什么**，并指向具体的失效路径 | ✅ `DbMigrations.MIGRATION_7_8` 的 KDoc |

**不做会怎样**：修好崩溃（按 `atHome` 过滤）之后，用户原来能看见的宠物会突然只剩 1 只 ——
崩溃变成「静默丢宠」，更难被发现。

**做了会怎样**：家里站 6 只，其余进「院子」，场景左上角出现「院子里还有 N 只 ›」。

> ⚠️ **V2 是一次事故修复的产物，不是新功能。**
> ADR-023「灵血传承」在**领域层**早已实现且测试齐全（`ExoticBloodRulesTest` 16 例），
> 但持久化层漏了：`PetEntity` 没有 `exotic_blood` 列、`PetMapper` 也没有映射。
> 后果非常隐蔽 —— 单元测试全绿（它们直接构造领域对象，**不经过数据库**），
> 而真实运行时宠物一旦落库再读出来，灵血浓度就被静默重置为 `0`，机制完全失效。
> 现已由 `PetMapperTest` 的往返测试守住，见 §5.4。

> ⚠️ **V3 又一次踩了同一个坑的边界**：ADR-026 把神兽形态改成"出生时结算的个体特征"，
> 而它**同样需要落库**。这次没有重犯 —— 领域字段、`PetEntity` 列、`PetMapper` 双向映射、
> 迁移、往返测试**在同一次改动里全部补齐**。`PetMapperTest` 已有
> `deity form flag survives a round trip` 与 `deity id is only exposed for pets that actually have the form` 两例。

> ⚠️ **V4 又是一次"文档到处引用、代码一处没有"的补漏**：
> 性别从 v1.0 起就写在 PRD（§5.2「孵化时随机；配对需要一公一母」）、
> 06 §2.3、04 Phase 6 验收里，而且是**配对生育的硬前置条件**，
> 但代码里搜 `gender` / `性别` **零命中** —— 配对实际只校验了"成年 + 亲密度"。
> 现补上 `PetGender` + `Pet.gender` + `pet.gender` 列 + 迁移 + 双向映射 + 往返测试，

> 📌 存量数据由迁移脚本**随机**分配性别（`RANDOM() & 1`），不是统一给 0 ——
> 统一给"公"会造成不可逆死局（老玩家宠物全变公的，再也配不上对）。详见 §4.2。

### 5.2 Migration 编写规范

```kotlin
// core/db/DbMigrations.kt —— 实际的迁移集合
val MIGRATION_1_2: Migration = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "ALTER TABLE `pet` ADD COLUMN `exotic_blood` INTEGER NOT NULL DEFAULT 0"
        )
    }
}

val MIGRATION_2_3: Migration = object : Migration(2, 3) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "ALTER TABLE `pet` ADD COLUMN `deity_form` INTEGER NOT NULL DEFAULT 0"
        )
    }
}

val MIGRATION_3_4: Migration = object : Migration(3, 4) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE `pet` ADD COLUMN `gender` INTEGER NOT NULL DEFAULT 0")
        // 存量数据随机分配，避免"老玩家宠物全是公的"这种不可逆死局
        db.execSQL("UPDATE `pet` SET `gender` = (RANDOM() & 1)")
    }
}

/** 全部迁移，按版本顺序注册 */
val ALL: Array<Migration> = arrayOf(MIGRATION_1_2, MIGRATION_2_3, MIGRATION_3_4)
```

**加表时的写法**（供后续阶段参考）：

```kotlin
val MIGRATION_4_5 = object : Migration(4, 5) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("""
            CREATE TABLE IF NOT EXISTS `user` (
                `id` INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
                `nickname` TEXT NOT NULL,
                ...
            )
        """)
        db.execSQL("CREATE INDEX IF NOT EXISTS `idx_user_remote` ON `user`(`remote_id`)")
    }
}
```

**红线**：

- ❌ 严禁**在正式包**挂载 `fallbackToDestructiveMigration()` —— 会清空用户数据
- ✅ 每个版本必须提供 Migration，并在 `AppModule` 中注册
- ✅ `exportSchema = true` 已开启，且 `core/build.gradle.kts` 已配置 `ksp { arg("room.schemaLocation", ...) }`，
  schema JSON 输出到 `core/schemas/com.sproutpet.core.db.SproutPetDatabase/`，**必须提交到版本库**

```kotlin
// ⚠️ 现状：仅在 DEBUG 构建挂载兜底，正式包缺失迁移时直接崩溃（fail fast）
val builder = Room.databaseBuilder(context, SproutPetDatabase::class.java, DB_NAME)
    .addMigrations(*DbMigrations.ALL)

if (com.sproutpet.core.BuildConfig.DEBUG) {
    builder.fallbackToDestructiveMigration()
}
return builder.build()
```

> 📌 早期骨架在**所有构建**上无条件挂了 `fallbackToDestructiveMigration()`，
> 而四处文档都声称"已移除" —— 这是本仓库里**最危险的一处文档失真**：
> 它的后果不只是"可能清库"，更是**掩盖"字段没落库"事故的元凶**
> （清库后老行没了，读取端看不到异常，问题被藏到线上）。
>
> 现在改为**只对 DEBUG 生效**：开发期保留"宁可清库也不崩溃"的便利，
> 正式包则**缺失迁移必须崩溃**，让问题在打包时就暴露。

### 5.4 映射一致性测试（JVM 层，比 Migration 测试更早拦截）

`MigrationTestHelper` 需要设备（Instrumented），跑得慢。所以在**纯 JVM 单测**里再加一层：

`PetMapperTest` 直接验证「领域对象 → 实体 → 领域对象」的字段无损，覆盖全部字段，
并对 `exoticBlood` 的 0~3 每个档位、`hasFullDeityForm` 的两个取值分别断言：

```kotlin
@Test
fun `exotic blood survives a round trip`() {
    for (blood in 0..MAX_BLOOD) {
        val original = samplePet(exoticBlood = blood)
        val restored = PetMapper.toDomain(PetMapper.toEntity(original))
        assertEquals(blood, restored.exoticBlood)
    }
}

@Test
fun `deity form flag survives a round trip`() {
    for (flag in listOf(false, true)) {
        val original = samplePet(rarity = Rarity.MUTANT, hasFullDeityForm = flag)
        val restored = PetMapper.toDomain(PetMapper.toEntity(original))
        assertEquals(flag, restored.hasFullDeityForm)
    }
}
```

## 六、查询优化要点

| 场景 | 优化手段 |
|------|---------|
| 首页主宠物 | `observeMainPet` 用 `ORDER BY is_hatched ASC, power DESC LIMIT 1`，走 `idx_pet_hatch_owner` |
| 排行榜 Top 100 | 走 `idx_pet_power` 索引，避免全表排序 |
| 我的排名 | `SELECT COUNT(*)+1 WHERE power > ?` —— 需索引支持 |
| 族谱树 | 先查 `family_id` 取全量，再在内存构建树（避免递归 SQL） |
| 每日统计 | 走 `UNIQUE(owner_id, stat_date)` 索引，O(1) 查询 |
| 待同步记录 | 走 `is_synced = 0` + `updated_at` 复合索引 |
