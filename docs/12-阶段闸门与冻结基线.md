> 版本：**v1.0**（新建）｜ 文档状态：**生效** —— 本文件是**执行顺序的唯一真相源**
> 更新日期：2026-10-16
> 配套文档：**全部 13 份**（本文件不描述「做什么」，只描述「按什么顺序做、什么时候算做完」）

## 〇、为什么有这份文档

产品方原话：

> 「先把产品需求》APP UI设计》宠物模型，确定下来，一定要把这些落实到文档中，
> 然后再调整开发计划》接口设计》代码研发》测试》验收。**一定要有一个顺序，这样不会乱的。**」

这句话解决的是本项目**真实发生过**的一类损失：

1. **反序施工** —— 在「抽蛋门票怎么定」还没拍板时，就去写了 `GachaRules` + 17 个单测
   （结论后来是对的，但顺序是反的：如果拍板结果不同，那 17 个测试全部作废）。
2. **层间复述** —— UI 设计稿把上游的金币数抄了一遍，于是漂移出
   「全勤 +735 金币」（真值 710，735 其实是**经验**合计）与「Lv.26 经验 18,370」（真值 6,238）。
   根因不是画错，是**下游抄数字而不是引用数字**。
3. **抢跑产物被当成基线** —— 下游已产出 226 例测试、V4 迁移，但它们建立在**上游尚未冻结**的口径上。
   上游一改，它们需要跟着改，而没人知道要改哪些。

**一句话规则**：上游没冻结，下游的一切产出都只是「草稿」，不是「基线」。

## 一、八阶段模型：一条冻结线把项目劈成两半

```
        ┌──────────────────────────────────────────────┐
        │  L1  产品需求      「要什么」                  │
        │  L2  APP UI 设计   「长什么样、怎么操作」        │  上游基线
        │  L3  宠物模型      「被操作的那个东西是什么」     │  Baseline
        └──────────────────────────────────────────────┘
════════════════════ 冻 结 线（Baseline Gate） ════════════════════
        ┌──────────────────────────────────────────────┐
        │  L4  开发计划      「谁在什么时候做」           │
        │  L5  接口设计      「模块之间怎么接」           │
        │  L6  代码研发      「写出来」                  │  下游交付
        │  L7  测试          「证明它对」                 │  Delivery
        │  L8  验收          「确认它就是要的东西」        │
        └──────────────────────────────────────────────┘
```

**为什么 L1~L3 在上游**：这三层回答的是**产品事实**，改动代价以「天」计（要重画、重测、重排期），
且**都不能由 AI 单方面决定**。

**为什么 L4~L8 在下游**：它们回答的是**实现路径**，全部是 L1~L3 的函数 ——
同一个需求可以有十种排期、十种接口设计，但只有一种产品事实。

## 二、四条闸门硬规则

### 🔒 R1 · 上游冻结才可开工下游
`L(n)` 的**冻结**是 `L(n+1)` 的**准入条件**。未过闸门的产出**一律标记为「草稿」**，
不得被下游引用为基线。

> 例外：**技术预研**（如 `99-桌宠技术验证操作单`）可以在上游未冻结时做 ——
> 因为它产出的是**可行性事实**，不是产品承诺。预研结论回填 L1 或 L3。

### 🔒 R2 · 下游不得复述上游的数字
下游文档 / 设计稿 / 代码**引用**上游数值时必须写明来源（如「= `GachaRules.GOLD_PRICE_PER_BOX`」），
**不得另抄一份**。裸数字只允许出现在**唯一真相源**那一处。

> 这条是 735/710、18,370/6,238 两次漂移的正面解法。UI 稿上出现数字时，
> 必须在标注里给出出处，否则视为未完成。

### 🔒 R3 · 冻结 = 三件套齐全
一个阶段算「冻结」，必须同时满足：

| 项 | 含义 |
|---|------|
| ✅ **版本号** | 该层真相源文档 bump 到冻结版，并在版本说明里写明「本次冻结」 |
| ✅ **零未决** | `09` 中归属该层的条目 **= 0**（全部收敛或明确挂起） |
| ✅ **可判定验收标准** | 该层有客观的「做完没做完」判据，不依赖主观感受 |

### 🔒 R4 · 变更必须回流，禁止就地绕过
下游发现上游有问题时：

```
下游发现 → 登记进 09-待决问题总表（带 L 层标签）
        → 回到对应上游层修改
        → 上游重新冻结（bump 版本号）
        → 再向下游逐层传播
```

**禁止**：在下游「顺手修一下」上游的口径。那会让两层文档同时说谎，
而且下游的修复通常不会回写到上游。

## 三、各阶段的冻结标准与现状

### L1 产品需求 🔴 **未冻结**

**冻结标准**
1. `00` 全文无 `⏳` / 「待拍板」/「建议（未转正）」标记
2. `09 §一` 中归 L1 的条目 = 0
3. `00` 里出现的每个数值，要么是唯一真源，要么标注了出处（R2）
4. `00 §八` 列出的每个「核心体验入口」，在 L2 都能找到对应的屏

**当前差距**：**6 项待拍板**（`U-02` 心情 / `U-03` 亲密度衰减 / `U-06` wisdom+charm /
`U-07` 隐居时机 / `U-09` 性别自纠错 / `U-11` 桌宠引导 + 「家 vs 桌宠」关系）
→ 明细见 [`09 §一`](./09-待决问题总表.md) 与本文 §五 Step 1

---

### L2 APP UI 设计 🔴 **未冻结**

**冻结标准**
1. `00 §八` 新手引导的**每一步**都有对应屏，且能串成流程
2. PRD 钦定的核心入口 —— **「把宠物放到手机桌面」（`U-11`）** —— 有完整流程屏
   （引导 → 授权 → 过渡 → 管理 → 拒绝兜底）
3. 每屏出现的**每个数字**都标注了来源（R2）
4. 成文：手势规范 / 页面过渡 / **空态** / **错误态** / **权限拒绝兜底**

**当前差距**
- ❌ `U-11` 桌宠引导 **3 屏未画**（两版设计稿共 25 屏，零覆盖）
- ⏳ `U-10` 倒置 IA 已拍板，但「**「家」与「桌宠」谁是主界面**」这句关系未定死（`U-11` 附问）
- ⏳ 手势 / 过渡 / 兜底态未成文（散落在 `gen.py` 各函数里）

---

### L3 宠物模型 🔴 **未冻结**

**冻结标准**
1. **每个字段**：定义 + 存储（列）+ 迁移 + mapper + 往返测试，一次做完
   （「派生但必须持久化」，`exotic_blood` 事故的教训）
2. **每条规则都有消费者** —— 禁止「写了但没人调用」
   （`isFirstPet` 漏传 / `MAX_FOCUS_BOOST_RATIO` 死常量 / `ItemEffect` 八种无执行层）
3. `09 §二` 中归 L3 的条目 = 0
4. 一切天数 / 概率以 `tools/acquisition_sim.py` 复算为准（ADR-024）

**当前差距**：**6 项机制缺位**

| 编号 | 缺什么 | 归属 |
|------|-------|------|
| `G-03` | `generation` 只存不算（永远 = 1） | L3 |
| `G-05` | `is_main` / `home_slot` / `desktop_slot` 三字段 | L3 |
| `G-06` | 属性只算一次（升级/互动/道具三条途径全无消费者）→ **与 `U-06` 是同一件事的两面** | L3 + L1 |
| `G-07` | `ItemEffect` 八种效果全部无执行层 | L3 |
| `G-08` | 玩具（`ItemCategory.TOY`）一件都没有 | L3 |
| `G-12` | 多只宠物站位布局算法完全缺位（家 6 / 桌面 3 两种规模） | L3 + L2 |

---

### L4 开发计划 🟡 **已存在，但基于未冻结的基线**

**准入**：L1 + L2 + L3 **全部冻结**（当前不满足）

**准出**：每个 Phase 的每个任务，都能反查到
「L1 的某条需求 / L2 的某屏 / L3 的某个模型」——
反查不到的任务就是「凭感觉加的」，删掉或补需求。

**当前状态**：`04` 内容详实（含 9 个 Phase、附录 A 日志、附录 B 风险、附录 C ADR），
但 **L1~L3 未冻结 ⇒ 全部任务只是草稿**。

### L5 接口设计 🟡 **部分**

**准出**：① 模块契约与端口；② DTO 与错误码；③ 线程 / 协程 / 生命周期约定；
④ 每个 `core` 对外暴露的能力都有签名与前置条件。

**当前状态**：`01` 有分层与目录规范，`03` 有 DAO 定义；
但 L1~L3 定稿后需**回头对账**（尤其 `G-05`/`G-07` 会新增字段与执行层接口）。

---

### L6 代码研发 ⚠️ **已抢跑**

**准入**：L5 冻结

**当前状态**：`core` 226 例测试 / `app` 可 `assembleDebug` / DB V4 + 3 条迁移。
**这些产出建立在上游未冻结的口径之上** —— 必须标注为**草稿基线**。
`U-06` 一旦按建议拍板（删除 `wisdom`/`charm` 的影响声明），`PetAttributes` 相关测试要跟着改。

> 诚实的说明：抢跑**不一定**白做 —— 领域层算法（保底、遗传、融合、节奏）是**产品事实的数学**，
> 命中率高。但**涉及「要不要有这个字段/这个规则」的部分**（U-06 影响声明、G-06 属性消费者、
> G-07 道具执行层）命中率低，因为那是**拍板之后才知道**的。

### L7 测试 ⚠️ **已抢跑**

## 五、解冻行动清单（按顺序执行，不可跳步）

### Step 1 · 产品方一次性拍板 L1 的 6 项 ⭐ **当前卡在这一步**

每项已压缩为一句话，**回一句「都按建议」即可全部转正**：

| 编号 | 待定 | AI 建议（默认值） | 拍板后影响 |
|------|------|-----------------|-----------|
| `U-02` | 「心情」没有数据模型 | 做成 `mood` 属性（**0~100**），**只影响行为表现权重**（Blend Tree emotion 通道），**不影响数值产出**（守 ADR-021） | 新增 1 字段 + 1 迁移 + 表现层权重表 |
| `U-03` | 亲密度是否衰减 | **不衰减**。只让**表现**随久未互动变化（背对 / 不理人），**不扣数值** | 纯文档，零代码 |
| `U-06` | `wisdom` / `charm` 的影响声明无实现 | **删除这两条影响声明**，降为**纯展示属性**（只参与 `power` 排行分）。⚠️ 与 `G-06` 同批处理 | 删声明 + 可能调整 `PetAttributes` 与相关测试 |
| `U-07` | 隐居触发条件的「一段时间」 | **不自动隐居**。到 Lv.60 只提示「可以入后山了」，**是否隐居由用户决定**（与融合「入后山」语义统一） | `RetirementRules` 去掉定时器 |
| `U-09` | 性别是硬门槛但无纠错通道 | ① **NPC 搭档性别永远取反**（成本为零，**必做**）；② **改性别道具提前到 Phase 2~3** | ① 1 行代码 ② 新增 1 道具 |
| `U-11` | 桌宠引导无设计；「家 vs 桌宠」关系未定 | ① 宠物**自己开口请求**（不做权限清单页）② 授权后有「跳出去」过渡 ③ 抽屉补「桌面宠物」入口 ④ 拒绝授权要有兜底与再次引导 ⑤ ⭐ **「家」是主界面，桌宠是「家」的延伸窗口**，同一份数据两个可见位置 | L2 补 3 屏 + L1 写死关系句 |

## 六、抢跑复盘（4 个真实案例，供今后识别同类问题）

| # | 发生了什么 | 违反了哪条 | 正确做法 |
|---|-----------|-----------|---------|

> 属于**数学推导**的（保底期望抽数、遗传分布），抢跑大概率命中，但仍需在冻结后复核。
