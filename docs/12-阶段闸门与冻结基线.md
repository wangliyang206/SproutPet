## 〇、为什么有这份文档

产品方原话：

> 「先把产品需求》APP UI设计》宠物模型，确定下来，一定要把这些落实到文档中，
> 然后再调整开发计划》接口设计》代码研发》测试》验收。**一定要有一个顺序，这样不会乱的。**」

这句话解决的是本项目**真实发生过**的一类损失：

1. **反序施工** —— 在「抽蛋门票怎么定」还没拍板时，就去写了 `GachaRules` + 17 个单测
   （结论后来是对的，但顺序是反的：如果拍板结果不同，那 17 个测试全部作废）。
2. **层间复述** —— UI 设计稿把上游的金币数抄了一遍，于是漂移出
   「全勤 +735 金币」（真值 710，735 其实是**经验**合计）与「Lv.26 经验 18,370」（真值 6,238）。
   根因不是画错，是**下游抄数字而不是引用数字**。
3. **抢跑产物被当成基线** —— 下游已产出 262 例测试、V5 迁移；其中一部分写于**上游尚未冻结**时，现已随三层冻结逐条回对账（处置见 §三 L6）。**教训仍成立：先冻结口径，再写实现。**
   上游一改，它们需要跟着改，而没人知道要改哪些。

**一句话规则**：上游没冻结，下游的一切产出都只是「草稿」，不是「基线」。

## 一、八阶段模型：一条冻结线把项目劈成两半

```
        ┌──────────────────────────────────────────────┐
        │  L1  产品需求      「要什么」                  │
        │  L2  APP UI 设计   「长什么样、怎么操作」        │  上游基线
        │  L3  宠物模型      「被操作的那个东西是什么」     │  Baseline
        └──────────────────────────────────────────────┘
════════════════════ 冻 结 线（Baseline Gate） ════════════════════
        ┌──────────────────────────────────────────────┐
        │  L4  开发计划      「谁在什么时候做」           │
        │  L5  接口设计      「模块之间怎么接」           │
        │  L6  代码研发      「写出来」                  │  下游交付
        │  L7  测试          「证明它对」                 │  Delivery
        │  L8  验收          「确认它就是要的东西」        │
        └──────────────────────────────────────────────┘
```

**为什么 L1~L3 在上游**：这三层回答的是**产品事实**，改动代价以「天」计（要重画、重测、重排期），
且**都不能由 AI 单方面决定**。

**为什么 L4~L8 在下游**：它们回答的是**实现路径**，全部是 L1~L3 的函数 ——
同一个需求可以有十种排期、十种接口设计，但只有一种产品事实。

## 二、四条闸门硬规则

### 🔒 R1 · 上游冻结才可开工下游
`L(n)` 的**冻结**是 `L(n+1)` 的**准入条件**。未过闸门的产出**一律标记为「草稿」**，
不得被下游引用为基线。

> 例外：**技术预研**（如 `99-桌宠技术验证操作单`）可以在上游未冻结时做 ——
> 因为它产出的是**可行性事实**，不是产品承诺。预研结论回填 L1 或 L3。

### 🔒 R2 · 下游不得复述上游的数字
下游文档 / 设计稿 / 代码**引用**上游数值时必须写明来源（如「= `GachaRules.GOLD_PRICE_PER_BOX`」），
**不得另抄一份**。裸数字只允许出现在**唯一真相源**那一处。

> 这条是 735/710、18,370/6,238 两次漂移的正面解法。UI 稿上出现数字时，
> 必须在标注里给出出处，否则视为未完成。

### 🔒 R3 · 冻结 = 三件套齐全
一个阶段算「冻结」，必须同时满足：

| 项 | 含义 |
|---|------|
| ✅ **版本号** | 该层真相源文档 bump 到冻结版，并在版本说明里写明「本次冻结」 |
| ✅ **零未决** | `09` 中归属该层的条目 **= 0**（全部收敛或明确挂起） |
| ✅ **可判定验收标准** | 该层有客观的「做完没做完」判据，不依赖主观感受 |

### 🔒 R4 · 变更必须回流，禁止就地绕过
下游发现上游有问题时：

```
下游发现 → 登记进 09-待决问题总表（带 L 层标签）
        → 回到对应上游层修改
        → 上游重新冻结（bump 版本号）
        → 再向下游逐层传播
```

**禁止**：在下游「顺手修一下」上游的口径。那会让两层文档同时说谎，
而且下游的修复通常不会回写到上游。
